# 播放截止时间

> [!tip] 阅读提示
> **前置：** [[基础与媒体地图]]、[[端到端延迟]]；时间轴见 [[时钟与时间戳]]。
> **初读：** 先读「一句话说明」「问题边界」「核心机制」，弄清截止时间解决什么、不负责什么。
> **深入：** 工作流程、音视频差异、工程取舍与观测，在实现、联调或排障时再读。

## 一句话说明

播放截止时间是某个媒体单元仍能被接收、恢复、解码并按计划呈现的最后时刻，它决定 RTC 为什么不能无限等待可靠交付。

## 问题边界

- **上游：** 播放时钟与目标缓冲、媒体时间（RTP timestamp / 采样时长）、当前抖动与 RTT 估计。
- **下游：** 是否发起 NACK/RTX/FEC 等待、是否 PLC/丢弃/跳帧、是否请求关键帧（PLI/FIR）。
- **本概念回答：** 一个迟到或丢失的单元还值不值得恢复？“恢复成功”与“恢复后仍然太晚”如何区分？
- **本概念不负责：** 端到端总预算拆解（见 [[端到端延迟]]）、拥塞如何改码率（见 [[GCC]]）、NetEQ 内部算法细节（见相关音频笔记）。
- **易混淆：**
  - 截止时间 ≠ 报文到达时间；它是从播放时钟反推的剩余预算。
  - 网络层“已恢复” ≠ 用户可感知无损伤（仍可能晚于截止）。
  - RTT ≠ 恢复全耗时（还含排队、重传调度、解码、渲染）。

## 核心机制

接收端根据媒体时间、目标缓冲和当前播放时钟估算截止时间。发现丢包后，只有预期重传到达加上解码余量仍早于截止时，NACK/RTX 才有实际价值；否则应丢弃、隐藏或请求新的可解码起点。

```text
playout_deadline ≈ media_time_mapped + target_buffer_slack
useful_recovery  <=> ETA(recovery) + decode/render_margin < playout_deadline
```

增加缓冲会提高迟到包命中率，却直接增加交互延迟；减少缓冲则降低延迟，却让抖动和恢复余量变小。系统在**连续性**与**交互性**之间用截止时间做显式决策。

```mermaid
flowchart LR
    L["发现包或帧缺失"] --> E["估算恢复完成时间<br/>网络往返 + 排队 + 解码/渲染余量"]
    E --> J{"预计完成时间<br/>早于播放截止？"}
    J -- 是 --> W["发送 NACK 或等待 FEC"]
    W --> P["及时恢复后播放"]
    J -- 否 --> S["停止等待<br/>隐藏、丢弃或请求新起点"]
    S --> A["推进播放时钟<br/>避免后续媒体一起变晚"]
```

## 工作流程

1. 接收端根据播放时钟和缓冲目标，为下一音频包或视频帧估算可用的播放窗口。
2. 报文缺失时，查询重传、FEC 或丢包隐藏的预计到达时间，并加上排队、解码和渲染余量。
3. 若恢复完成时间早于截止时间，发送恢复请求或等待冗余；否则跳过该数据，推进解码器和播放时钟。
4. 视频恢复还要检查参考帧链：一个迟到的 P 帧可能影响后续帧，关键帧请求的代价也应计入预算。
5. 持续统计截止时间命中率，动态调整抖动缓冲、恢复策略和发送质量。

## 关键对象与数据

| 对象 | 描述“什么” |
| --- | --- |
| 媒体时间 | RTP timestamp、采样时长、帧持续、播放序号 → 应何时播放 |
| 本地时间 | 接收、预计恢复、解码、渲染排队、单调时钟 → 还来不来得及 |
| 恢复请求 | NACK/RTX 关联序号；FEC 冗余窗口；PLI/FIR 新起点 |
| 结果分类 | 未丢失 / 及时恢复 / 恢复但迟到 / 无法恢复 / 恢复导致后续阻塞 |

决策必须在**同一单调时间轴**上计算；跨机器对比先处理时钟偏移。详见 [[时钟与时间戳]]。

## 音频与视频差异

| 维度 | 音频 | 视频 |
| --- | --- | --- |
| 超时后手段 | PLC/FEC 生成连续输出 | 丢弃、跳帧、等参考或要关键帧 |
| 依赖 | 短时连续更重要 | 参考链使“一帧晚”可污染后续 |
| 关键帧成本 | 通常无 | 码率峰值，可能反加重拥塞 |
| 缓冲策略 | 更贴近固定输出节奏 | 可按帧类型差异化等待 |


## 与抖动缓冲、恢复策略的分工

- [[抖动缓冲]] 决定**目标深度**与播放时钟推进节奏，从而改变截止时间的松紧。
- [[丢包恢复策略]] 决定在预算内选 NACK、FEC、PLC 还是要关键帧；截止时间是它们的**准入门闩**。
- 本篇不替代上述两篇的算法细节：这里只强调“来不来得及”的判决口径与观测拆分。

## 工程要点与取舍

- 使用同一单调时钟计算接收、恢复、解码和渲染耗时；跨端测量时先处理偏移与方向。
- 恢复请求应受速率限制，避免丢包突发时反向拥塞；**只请求仍可能及时到达的数据**。
- 音频优先保证固定输出节奏；视频按帧类型和依赖关系决定丢弃、跳帧或请求关键帧。
- 在弱网下把截止时间命中率、卡顿和端到端延迟一起优化，不能只追求恢复率。
- 指标应区分网络丢包、恢复成功、恢复后仍晚到和最终可感知损伤。

## 常见误区与故障表现

| 误区 | 表现 |
| --- | --- |
| 所有丢包都重传 | 重传过期，白占带宽，延迟升高 |
| 用 RTT 直接当恢复耗时 | 低估排队/解码/渲染，决策过于乐观 |
| 只统计网络层丢包 | 本地队列溢出、解码过载、晚到丢弃被漏计 |
| 关键帧请求过于频繁 | 码率峰值 → 更拥塞 → 更多截止失败 |
| 缓冲只升不降 | 交互变慢，用户觉得“慢半拍” |

## 观测与验证

- 记录 deadline、arrival、recovery-request、recovery-arrival、decode-start、render 时间戳及其差值。
- 分别统计 NACK/RTX/FEC/PLC 使用次数、及时恢复率、迟到恢复率、关键帧等待时长和连续卡顿时长。
- 与接收 jitter、队列深度、RTT、丢包率和编码码率关联，判断是窗口过小还是链路过载。
- 用可重复的延迟、抖动和突发丢包注入，验证不同播放缓冲和恢复策略的临界点。
- 成功标准：提高恢复率的同时，迟到恢复占比下降或可解释；E2E 延迟不无界爬升。

## 具体例子

某音频包在 20 ms 播放周期下丢失，估计 RTX 往返 45 ms，而当前只剩 18 ms 的播放余量。此时发送 NACK 没有收益，应使用 PLC 继续输出；如果后续多个包连续丢失，再通过 FEC 或调整缓冲恢复连续性，并记录“隐藏而非及时恢复”。视频侧若参考帧已过截止，与其死等 RTX，不如评估 PLI 成本是否小于后续花屏时长。
