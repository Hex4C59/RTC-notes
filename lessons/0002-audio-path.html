声音中途还需要怎样整理？

本课在采集、处理、编码、发送、接收、解码与播放之间补充两个位置：发送前打包，接收后缓冲。

简化模型：采集 → 预处理 → 编码 → 打包发送 → 网络 → 接收拆包、重排与缓冲 → 解码 → 输出播放。

这是理解职责的简图，不是要求实现严格划分成这些模块，也省略了加密等细节。本课暂把音频渲染与设备播放合并讨论，不额外增加一个必须独立存在的环节。

打包：不只发送内容

假设你的电脑陆续产生三段声音。接收端不仅要拿到声音内容，还需要知道包的顺序和媒体时间位置。RTP 为媒体包提供序列号、时间戳等信息。序列号不是时间戳，也不等于一段话的编号。

缓冲：收到顺序未必是播放顺序

网络可能让包到达得忽快忽慢，甚至顺序颠倒。接收端需要结合包的信息与播放时序安排输出，而不是把先到的声音无条件先播。等待也有延迟代价，不能无限等。

依据：RFC 3550 §2.1；先看音频会议示例，不要求记报头字段。

练习：先回答再看提示

为方便理解，假设“你”“好”“呀”分别放在三个包里（真实编码并不按汉字分包）。发送顺序为“你 → 好 → 呀”，到达顺序却是“你 → 呀 → 好”。若每收到一个包就立刻解码播放，会出现什么问题？你希望接收端先做什么？

回答后查看提示

按到达顺序直接播，会让示例内容的先后颠倒。若“好”能在播放需要它之前赶到，可以利用顺序信息和有限缓冲安排正确播放；若赶不上，就必须另行处理缺失，不能无限等待。此例只解释顺序，不讨论真实编码依赖。
