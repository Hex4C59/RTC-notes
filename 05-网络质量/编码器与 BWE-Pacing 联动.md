# 编码器与 BWE-Pacing 联动

> [!tip] 阅读提示
> **前置：** [[带宽估计]]、[[GCC]]、[[Pacing]]、[[带宽分配]]。
> **初读：** 先读“一句话说明”“问题边界”“闭环”和“延迟耦合”，理解目标码率如何变成编码器配置与发送队列。
> **深入：** ALR、层切换、关键帧峰值、版本化目标在弱网排障时再读。

## 一句话说明

拥塞控制给出的网络目标码率，必须经带宽分配与 Pacing，再落到编码器（及 SVC/Simulcast 选层）的实际产出；三者脱节会出现“估计很高但发不出去”或“编码很低却把 pacing 队列堆爆”。本篇只谈联动，不展开单一拥塞公式或单一编码器原理。

## 问题边界

- **上游：** TWCC/RTCP 反馈、[[GCC]] / [[带宽估计]] 输出的 target、RTT、丢包、ALR 标记。
- **下游：** 编码器 target bitrate / QP / 帧率 / 层、Pacer 队列深度、线上实际发送码率。
- **易混淆：**
  - 网络 target ≠ 编码器瞬时产出 ≠ 线路吞吐。
  - 应用受限（ALR）时低发送 ≠ 带宽变差。
  - 关键帧/FIR 造成的码率尖峰 ≠ 稳态目标。
  - 「Stats 里 bitrate 很高」可能是估算窗口，不等于 pacer 已送出。

## 核心机制

```text
反馈 -> BWE/GCC target
     -> 带宽分配（媒体 / RTX / FEC / probing）
     -> 编码器目标与层选择
     -> 编码出包
     -> Pacing 平滑发送
     -> 网络队列与新反馈
```

闭环的每一跳都有**延迟**与**版本**：反馈有年龄，编码线程有队列，pacer 有泄放速率。联动质量取决于“新目标何时真正约束下一帧”，而不是日志里是否打印过一次 target。

### 延迟耦合点

| 耦合点 | 若断裂的现象 |
| --- | --- |
| BWE → 分配 | 修复/探测挤占后媒体预算未下调，视频仍高码率 |
| 分配 → 编码 | 编码器仍按旧码率产帧，pacer 队列飙升 |
| 编码 → Pacing | 大帧一次性注入，发送突发制造假拥塞 |
| Pacing → BWE | 应用没数据（ALR）被当成带宽下降 |

## 关键对象与数据

| 名称 | 典型用途 |
| --- | --- |
| `target_bitrate` | BWE 网络目标 |
| 媒体 / RTX / FEC 预算 | [[带宽分配]] 扣除后的可用媒体码率 |
| `pacing_rate` | 常略高于媒体，吸收突发与探测 |
| 编码器 target / QP / fps | 实际产帧约束 |
| 层 / RID | Simulcast/SVC 选层 |
| pacer queue delay/bytes | 发送侧积压健康度 |
| ALR、probe、关键帧债务 | 解释“低发送”是否可信 |

## 工作流程

1. 控制器更新网络目标，并标注反馈年龄与置信度。
2. 分配器扣除保护/探测后，得到每路媒体预算（多流时按优先级拆分）。
3. 编码器在下一关键边界或立刻（视实现）应用新目标；SVC/Simulcast 决定升降层。
4. 产出帧进入 pacer；按预算平滑，必要时丢弃可丢层或延迟非关键。
5. 新反馈验证：队列是否回落、丢失是否改善、ALR 是否误触发。

```text
target↓ fast path: allocate -> encoder ASAP -> drain pacer
target↑ slow path: probe/confirm -> raise encode -> keep queue low
```

## 关键帧、探测与 ALR

- **关键帧预算：** PLI/FIR 后预留峰值，避免与 probing 叠加把路径打爆；关键帧债务应在数帧内摊还。
- **探测 padding：** 占用分配额度时，媒体预算必须同步下调，否则“探测成功”建立在媒体过载上。
- **ALR（应用受限）：** 摄像头暂停、屏幕内容静止、编码器卡住都会让发送低于 BWE；应用侧应标记 ALR，避免 GCC 误降。细节见 [[GCC]] / [[Pacing]]，此处不展开公式。


## 同时间轴读数怎么对齐

排障时不要拿“某一秒的 BWE 最大值”对比“另一秒的编码均值”。建议固定同一 wall/monotonic 窗口：

1. 取 BWE target 的采样序列（含反馈年龄）。
2. 取编码器产出：编码完成时刻的帧大小折算 bps，而非配置值。
3. 取 pacer 发送：socket 写出或 pacer 记账速率。
4. 叠 queue delay：若 target 已降而 encode 仍高、queue 上升，即联动断裂。

把这四条画在一张图上，比单独看丢包率更快定位是“估计错了”还是“执行慢了”。

## 工程要点

- **版本化目标：** 异步编码线程必须携带目标版本号，旧回调不能覆盖新目标。
- **降码率要快、升码率要慢：** 与 GCC 增减策略一致，防止振荡。
- **屏幕共享 vs 摄像头：** 清晰度优先与帧率优先的分配策略不同；静止画面 ALR 更常见。
- **多流隔离：** 一人弱网不应把房间最低公共码率强加给所有订阅（SFU 场景见 [[带宽分配]]）。
- **观测同一时间轴：** 把 BWE target、encoder actual、pacer send rate 画在一起才有意义。

## 常见误区与故障表现

| 误区 | 故障表现 |
| --- | --- |
| 只调编码器不调 pacer | 本地队列暴涨，RTT/抖动看起来变差 |
| 只信 BWE 曲线 | ALR 期间误判弱网，恢复时过冲 |
| 层切换无迟滞 | 画质在阈值附近闪烁 |
| 关键帧+探测同时放开 | 短时丢包尖峰，尾延迟爆炸 |
| 多流共享一个最低公共码率 | 一人弱网拖垮房间 |

## 观测与验证

- **指标：** BWE target、allocated media、encoder output bps、QP、帧率、key frame bytes、pacer queue ms、发送码率、丢包、ALR。
- **实验：** 带宽阶跃下降/上升；插入关键帧；暂停摄像头制造 ALR；Simulcast 升降层。
- **成功标准：** 下降时队列与丢包先收敛；上升时不出现长时间 pacing 积压；三曲线（target / encode / send）同向且延迟可控。
- **对照：** [[WebRTC Stats]]、[[GCC 探测与码率控制状态机]]、[[弱网对抗]]。

## 具体例子

目标从 1.5 Mbit/s 降到 600 kbit/s。若编码器 2 秒后才响应，pacer 队列从 30 ms 涨到 200 ms，TWCC 显示到达间隔变差，BWE 可能进一步下降——形成“编码滞后 → 假拥塞 → 再降码率”的螺旋。正确做法是缩短目标应用延迟，并在过渡期允许丢弃非参考帧或暂时降帧率。反向升码时，先确认 pacer queue 低、无持续丢失，再抬编码器，避免刚恢复就过冲。
