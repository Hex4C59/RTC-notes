# GCC 探测与码率控制状态机

GCC 不是一个单独公式，而是由发送历史、到达反馈、吞吐确认、延迟趋势、丢包约束、探测控制、应用受限识别和码率控制共同组成的闭环。本页专门解释“何时探测、怎样使用确认吞吐、为什么速率会上升或下降”。

## 主要输入和输出

输入包括 TWCC 配对后的包级发送/到达样本、确认接收字节、丢包、反馈年龄、RTT、Pacer 队列、应用产出和编码器限制。输出通常是网络目标速率、Pacing 速率、探测计划和状态原因；它不等于编码器实际输出或用户可见画质。

## 关键估计量

- `delay_based_estimate`：根据包组相对到达延迟和过载检测得到的容量约束。
- `acknowledged_bitrate`：在反馈窗口内，接收端确认到达的有效字节除以对应到达时间跨度；窗口、突发、重传和探测包口径必须明确。
- `loss_based_estimate`：根据丢失及其窗口形成的另一约束，不能把无线随机丢包一律解释为排队拥塞。
- `network_estimate`：控制器合并各信号后的可发送参考，通常还带上下界和有效时间。
- `target_bitrate` 与 `pacing_rate`：前者用于预算，后者常高于媒体目标以便平滑发送和留出探测/恢复空间；具体倍数属于版本配置。

## 码率状态机

```text
未初始化
  └─ 获得起始估计/有效探测 -> Hold

Hold
  ├─ 稳定且有增长余量 -> Increase
  └─ 延迟过载/严重丢包 -> Decrease

Increase
  ├─ 反馈稳定 -> 有界增加
  ├─ 应用受限 -> 停止把低吞吐当成网络上限
  └─ 过载 -> Decrease

Decrease
  └─ 依据有效吞吐/估计快速降到安全范围 -> Hold
```

实际实现可能使用不同枚举和多个控制器，但必须保留“输入样本、旧状态、转换原因、新目标”四项日志，不能只记录最终码率。

## 探测控制器状态机

发送端通过一小段高于当前业务速率的 padding 或媒体突发观察链路是否能承载更高速率。常见触发包括初始建连、网络估计明显增大、最大码率上调、路由变化或从应用受限恢复。

```text
Idle
  └─ 满足触发且允许探测 -> WaitingForResult
WaitingForResult
  ├─ 反馈覆盖充分且结果有效 -> Success / 更新估计
  ├─ 反馈不足但仍在超时内 -> 等待
  └─ 超时、丢包或过载 -> Failed / 冷却
冷却后 -> Idle
```

探测流量必须经过 Pacer 并计入线上预算。关键帧自然突发不是受控探测；把它当作探测可能同时制造排队并高估可用容量。

## ALR：应用受限区域

当应用或编码器没有足够数据填满当前网络目标时，实际发送低于目标，这称为应用受限。此时低 acknowledged bitrate 不能直接证明网络容量下降。例如摄像头静止、视频暂停、编码器 CPU 受限或仅发送音频都会形成低发送量。

ALR 检测通常比较一段窗口内的实际发送量与目标预算，并设置进入/退出滞回。退出 ALR 后可能需要受控探测重新验证容量，不能沿用长期空闲前的高速估计无限发送。

## Acknowledged bitrate 的计算边界

简单形式是 `确认字节数 / 到达时间跨度`，但工程上必须处理：窗口首尾包、反馈聚合、到达时间量化、乱序、重复、RTX/FEC/padding 是否计入、应用受限和接收端反馈缺口。窗口太短会跟随突发抖动，太长会让容量变化响应迟缓。

确认吞吐是“这段时间实际送达多少”，不等于链路最大容量。若发送端只发 500 kbit/s，确认 500 kbit/s 不能证明网络只能承载 500 kbit/s；这正是 ALR 与 probing 必须存在的原因。

## 包组延迟和过载

对连续包组计算发送间隔差与到达间隔差，正的相对差持续增长说明网络中可能正在积累队列。趋势滤波器和阈值检测需要离群剔除、滞回和最小样本量。接收线程卡顿、反馈压缩和错误发送时间也可能制造相似信号，必须结合 Pacer、Socket 和 CPU 指标。

## 反馈丢失和过期

- 反馈在途时，不能立即把未覆盖包判为永久丢失。
- 反馈长期中断时，应冻结增长或保守降级，并标记 `feedback_stale`，不能用旧样本继续升速。
- 反馈恢复后先清除跨代次和超窗口发送历史，再形成新样本；网络切换前后的时间序列不能直接拼接。
- 发送历史必须有容量和超时，避免反馈缺失造成无界内存增长。

## 线程与工程实现

- 收包反馈解析、样本聚合和控制器更新应在明确的串行序列运行，确保一次反馈产生一个原子状态转换。
- 编码器配置、分层选择和 Pacer 更新可以异步执行，但要携带估计版本；旧任务不能覆盖新目标。
- 所有线上字节都要统一口径，包括 RTP/RTCP、SRTP、UDP/IP、RTX/FEC、padding、TURN 和隧道开销。
- 对目标变化设置最小/最大边界和速率限制，避免小样本导致分辨率、帧率和码率频繁振荡。

## 必需日志

每次更新记录：反馈覆盖范围与年龄、acknowledged bitrate、延迟趋势、过载状态、丢包估计、ALR 状态、探测 ID/目标/结果、旧目标、新目标、Pacer 队列、最终转换原因。多流时还要记录总预算怎样分配到音频、视频层和恢复流量。

## 故障注入与验收

1. 容量阶跃下降：观察过载检测、降速时刻、队列峰值和恢复时间。
2. 容量阶跃上升：验证没有探测时不盲目高估，有有效探测后能有界上升。
3. 应用静默后恢复：确认 ALR 内低吞吐不压低容量，退出时探测不过冲。
4. 反馈暂停、批量到达和乱序：确认旧反馈不驱动增速，发送历史正确清理。
5. 注入关键帧和 RTX 突发：确认其开销计费且不被错误解释为普通稳定吞吐。

## 常见误区

- “TWCC 就是 GCC”：TWCC 只提供逐包反馈，GCC 还包括估计与控制。
- “确认吞吐就是带宽上限”：发送不足时，它只是实际送达速率。
- “探测越多恢复越快”：探测本身会占带宽并可能造成排队。
- “目标码率下降代表线路负载下降”：RTX、FEC、padding 和协议开销可能抵消媒体降幅。
