# 带宽分配

带宽分配把拥塞控制给出的目标速率拆成可执行的线路预算，而不是把目标值原样交给编码器。线上总速率至少包括媒体、重传、FEC、padding/探测、RTCP 和各层封装开销。

## 基本预算

```text
总发送预算
  = 原始媒体 + RTX/重传 + FEC/冗余 + padding/探测 + RTCP/协议开销
编码器可用码率
  = 总发送预算 - 非编码流量的预留
```

预算必须明确统计窗口和字节口径，并为控制反馈和必要的修复流量留出上限。否则编码器看似没有超目标，重传或探测加入后仍会把 Pacer 队列推高。

## 多流与优先级

- 先按音频、主视频、辅视频、屏幕共享和数据通道设定最低保障与上限，再在可用余量中分配分层编码的空间。
- Simulcast/SVC 切换应把层的码率、关键帧成本和切换突发纳入预算，不能只比较稳态码率。
- 过载时优先保护仍有播放价值的媒体，降低层级或丢弃过期修复包；恢复流量要有配额，不能无限挤占新媒体。

## 观测闭环

同时记录目标预算、每类流量的实际字节、编码器目标、Pacer 队列和发送结果。GCC 的目标速率、应用约束、SFU 的订阅策略和线路封装开销必须分开，才能解释“目标码率很高但实际发送很低”或“编码码率正常但队列持续增长”。

## 端到端流程

1. 拥塞控制给出某个时间窗口的目标线上预算，应用层提供音频、视频、屏幕共享和数据流的优先级/上下限。
2. 分配器先为 RTCP、协议/安全封装、RTX/FEC、padding/探测预留额度，再把剩余预算交给编码器和分层选择。
3. Pacer 按各类流量的额度和截止时间发包，并回报实际使用；未使用额度、超限和过期包进入下一轮调整。
4. 观测层比较目标、实际、队列和 QoE，判断是网络受限、某流超卖、修复开销过高还是应用未产出。

## 预算口径

- 必须先声明目标是“编码媒体码率”还是“线上总码率”。若目标是线上总码率，所有 RTP/RTCP/SRTP/IP/UDP/隧道字节都从同一预算扣除。
- 可用媒体预算可写成 `media_budget = on_wire_budget - overhead - repair - probe - feedback`，每一项都要说明统计窗口和单位。
- 预留不是无限固定比例；音频连续性、关键帧、恢复截止和多流优先级可能需要动态调整。
- 任何模块产生的额外包都必须带类别、流、优先级和预算消耗，避免重复计费或漏计费。

## 数值示例

若线上目标为 2,000 kbit/s，协议/安全开销 120 kbit/s，RTCP 20 kbit/s，RTX/FEC 200 kbit/s，探测 100 kbit/s，则编码媒体预算约为 `2,000 - 120 - 20 - 200 - 100 = 1,560 kbit/s`。若把 2,000 kbit/s 直接交给编码器，线上负载必然超过目标。

一个 1,200 kbit/s 的视频层与 80 kbit/s 音频层共存时，不应只按比例切分剩余预算；应先保障音频和交互关键流，再在视频层间按订阅、分辨率和切换成本分配。

## 状态与实现

- 分配器维护总预算、已承诺预算、实际发送、欠账、流优先级、最小/最大码率和时间窗。
- Simulcast/SVC 层切换要把新层关键帧或刷新突发纳入一次性预算，不能只比较稳态层码率。
- 恢复流量要有上限和截止时间；过期 RTX/FEC 应释放额度给后续新媒体。
- SFU 的订阅变化、编码器不可达码率和 Pacer 背压都应反馈给分配器，而不是悄悄突破总预算。

## 常见误区与故障表现

- 误区：带宽分配就是给每个编码器设一个码率。线路还承载修复、反馈、探测和封装。
- 误区：按流平均分配就是公平。音频最低保障、屏幕共享交互和视频层优先级通常不同。
- 故障：编码器目标未超限但线上拥塞，检查漏算的封装、关键帧、RTX/FEC 和 padding。
- 故障：一条流码率突然归零，检查优先级、层切换、应用受限标记和预算借用/归还。

## 观测与实验

按时间窗记录总预算、媒体/音频/视频/修复/反馈/探测/封装字节、各流目标与实际、Pacer 队列和丢弃原因。实验覆盖单流、多流、Simulcast 切换、关键帧、突发丢包和带宽阶跃，验证总和不超过线上预算且优先级符合预期。
