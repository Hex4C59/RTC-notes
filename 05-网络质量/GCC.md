# GCC

GCC（Google Congestion Control）是 WebRTC 体系中一类以反馈观测驱动发送速率调整的拥塞控制实现路线，不应被理解成一个永远不变的单一公式。不同版本会调整反馈、滤波、过载判定、码率控制和发送调度的组合。

## 闭环

1. 接收端从传输反馈中汇总到达时刻、丢包、接收速率等样本。
2. 发送端根据延迟趋势和丢包状态估计网络是否过载，得到可用目标速率及其变化方向。
3. 码率分配把目标速率分给编码媒体、修复流量、反馈和探测；Pacer 再按预算把包平滑发出。
4. 新一轮到达观测验证队列是否收敛、体验是否改善，并抑制过快增速或降速振荡。

TWCC 是常见的逐包观测输入，REMB 可作为兼容性或较粗粒度的接收端码率提示；二者都不是 GCC 本身。延迟趋势检测、丢包控制和 AIMD/探测策略是可替换的实现部件，阅读源码时要记录具体版本和配置。

## 工程边界

GCC 输出的是控制参考或目标速率，不等于编码器实际码率、线路吞吐或用户体验指标。应用受限、CPU 编码受限、SFU 转发策略和多流竞争都可能让实际发送低于目标；需要把这些原因与网络过载分开观测。

## 端到端闭环

1. 接收端产生 TWCC/RTCP 反馈，发送端把反馈与发送历史配对，形成到达间隔、丢包和吞吐样本。
2. 延迟趋势检测器判断排队是否增长，丢包控制器提供另一条约束，估计器将结果合并为目标速率或状态。
3. 码率分配扣除控制和修复流量后通知编码器/分层器，Pacer 按线上预算发送。
4. 新反馈观察队列、实际接收和用户体验，控制器在增长/保持/下降状态间有界切换。

## 组成与边界

- 反馈层回答“包何时到、哪些包缺失”；TWCC、RTCP feedback 和 REMB 是不同粒度/语义的信号，不是 GCC 名称。
- 估计层回答“当前可承载多少”；延迟趋势、丢包、吞吐、探测和应用受限判断可以按版本组合。
- 控制层回答“怎样改变发送”；AIMD 或其他调节、码率分配和 Pacing 有各自状态与约束。
- GCC 输出的是控制参考，不等于编码器已经产出的码率、线路实际吞吐或 QoE；版本变动时必须记录源码提交和配置。

## 状态、时序与示例

控制器至少要保存目标速率、最近有效反馈时间、过载状态、估计置信/边界、应用受限标记和各流分配。反馈过期时应保持或保守降级，不能用旧样本继续增速。

若初始目标为 1.5 Mbit/s，连续反馈显示到达间隔增长、Pacer 队列从 20 ms 增到 100 ms，控制器应先进入过载/下降路径并降低媒体预算；若随后队列回落且接收稳定，再以受限速度增加。具体阈值和比例属于实现版本，不在笔记中假定固定常数。

## 发送侧与接收侧实现

- 接收侧只负责准确记录到达、丢失和反馈覆盖，不应把某个启发式估计值伪装成确定线路容量。
- 发送侧要区分网络受限、应用受限、编码器受限和 CPU 受限，并把原因传给控制器和 Stats。
- 码率控制、Pacer、重传和 FEC 必须共享预算，否则 GCC 输出下降仍可能被额外流量抵消。
- 多流/多订阅时要在总目标和每流分配之间建立优先级与最低保障，避免一条流占满全部预算。

## 常见误区与故障表现

- 误区：GCC 只有一个固定公式。它是实现体系，滤波、反馈、控制和版本都可能变化。
- 误区：GCC 只看丢包。现代实现常同时使用时延趋势、吞吐、反馈年龄和应用状态。
- 故障：网络恢复后速率不回升，检查旧反馈、探测受限、Pacer 队列和应用受限标记。
- 故障：速率振荡或关键帧后反复下降，检查突发、开销计费、趋势滤波和恢复流量。

## 观测与实验

每个控制周期记录反馈类型、样本窗口、延迟趋势、丢包、目标/实际速率、状态、各类预算、Pacer 队列和 QoE。实验覆盖理想网络、RTT 变化、容量阶跃、突发丢包、反馈丢失、应用空闲和竞争流，比较收敛时间与过冲。

## 最小验收清单

- 能把一轮反馈从传输序号、到达样本追踪到目标速率和 Pacer 队列。
- 能区分 TWCC、REMB、CCFB 和 GCC 的层次与输入输出。
- 能在反馈暂停、应用空闲和 CPU 受限时避免误判网络过载。
- 能用固定容量阶跃实验报告收敛时间、过冲、队列峰值和 QoE 变化。
