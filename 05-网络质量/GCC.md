# GCC

## 一句话说明

GCC（Google Congestion Control）是 WebRTC 体系中一类以反馈观测驱动发送速率调整的拥塞控制实现路线，不应被理解成一个永远不变的单一公式。不同版本会调整反馈、滤波、过载判定、码率控制和发送调度的组合。

## 问题边界

- **上游：** [[TWCC]] / RTCP 反馈、到达时刻、丢包、接收速率、应用产出与 Pacer 队列。
- **下游：** 目标速率或状态 → [[带宽分配]] → 编码器/分层 → [[Pacing]]。
- **易混淆：**
  - TWCC / REMB / CCFB 是反馈信号，不是 GCC 本身。
  - GCC 目标速率 ≠ 编码器实际码率 ≠ 线路吞吐 ≠ QoE。
  - 应用受限 / CPU 受限时低发送 ≠ 网络过载。
  - 延迟趋势检测、丢包控制、AIMD/探测是可替换部件；阅读源码要记录版本与配置。
  - 估计细节见 [[带宽估计]]；编码器联动见 [[编码器与 BWE-Pacing 联动]]，本篇不重复展开。

## 核心机制

### 闭环

1. 接收端从传输反馈中汇总到达时刻、丢包、接收速率等样本。
2. 发送端根据延迟趋势和丢包状态估计网络是否过载，得到可用目标速率及其变化方向。
3. 码率分配把目标速率分给编码媒体、修复流量、反馈和探测；Pacer 再按预算把包平滑发出。
4. 新一轮到达观测验证队列是否收敛、体验是否改善，并抑制过快增速或降速振荡。

```text
TWCC/RTCP 反馈
  -> 延迟趋势 + 丢包约束 + 吞吐
  -> 目标速率 / 增长|保持|下降
  -> 带宽分配 -> 编码/分层 -> Pacer
  -> 新反馈验证
```

### 组成与边界

| 层 | 回答的问题 | 常见部件 |
| --- | --- | --- |
| 反馈层 | 包何时到、哪些缺失 | TWCC、RTCP feedback、REMB |
| 估计层 | 当前可承载多少 | 延迟趋势、丢包、吞吐、探测、应用受限 |
| 控制层 | 怎样改变发送 | AIMD/调节、码率分配、Pacing |

GCC 输出的是控制参考，不等于编码器已产出码率、线路实际吞吐或用户体验。版本变动时必须记录源码提交和配置。工程边界：应用受限、CPU 编码受限、SFU 转发策略和多流竞争都可能让实际发送低于目标；需要把这些原因与网络过载分开观测。

### 端到端细化

1. 接收端产生 TWCC/RTCP 反馈，发送端把反馈与发送历史配对，形成到达间隔、丢包和吞吐样本。
2. 延迟趋势检测器判断排队是否增长，丢包控制器提供另一条约束，估计器将结果合并为目标速率或状态。
3. 码率分配扣除控制和修复流量后通知编码器/分层器，Pacer 按线上预算发送。
4. 新反馈观察队列、实际接收和用户体验，控制器在增长/保持/下降状态间有界切换。

### 状态、时序与示例

控制器至少保存：目标速率、最近有效反馈时间、过载状态、估计置信/边界、应用受限标记和各流分配。反馈过期时应保持或保守降级，不能用旧样本继续增速。

若初始目标为 1.5 Mbit/s，连续反馈显示到达间隔增长、Pacer 队列从 20 ms 增到 100 ms，应先进入过载/下降路径并降低媒体预算；若随后队列回落且接收稳定，再以受限速度增加。具体阈值和比例属于实现版本，不在笔记中假定固定常数。

| 状态倾向 | 典型触发 | 控制动作 |
| --- | --- | --- |
| 下降 | 延迟趋势过载 / 高丢包 / 队列飙升 | 快速下调媒体与探测预算 |
| 保持 | 反馈噪声大或刚切换 | 维持目标，避免抖动 |
| 增长 | 队列回落且接收稳定 | 受限增速，可配合探测 |

## 工程要点

- 接收侧只负责准确记录到达、丢失和反馈覆盖，不应把启发式估计伪装成确定线路容量。
- 发送侧区分网络受限、应用受限、编码器受限和 CPU 受限，并把原因传给控制器和 Stats。
- 码率控制、Pacer、重传和 FEC 必须共享预算，否则 GCC 输出下降仍可能被额外流量抵消。
- 多流/多订阅时在总目标和每流分配之间建立优先级与最低保障，避免一条流占满全部预算。
- 降速要快、增速要慢；关键帧与探测叠加时要防二次突发（细节链到分配与联动篇）。
- 能把一轮反馈从传输序号、到达样本追踪到目标速率和 Pacer 队列。
- 探测与码率控制状态机见 [[GCC 探测与码率控制状态机]]，此处不展开状态表。

## 常见误区与故障

| 误区 / 故障 | 表现与排查 |
| --- | --- |
| GCC 只有一个固定公式 | 滤波、反馈、控制和版本都可能变化 |
| GCC 只看丢包 | 常同时用时延趋势、吞吐、反馈年龄、应用状态 |
| 网络恢复后速率不回升 | 查旧反馈、探测受限、Pacer 队列、应用受限标记 |
| 速率振荡或关键帧后反复下降 | 查突发、开销计费、趋势滤波、恢复流量 |
| 把 REMB 当成整套 GCC | REMB 只是较粗粒度接收端码率提示 |
| 目标很高实际很低 | 分开看应用/CPU/层选择与网络过载 |

## 观测与验证

每个控制周期记录：反馈类型、样本窗口、延迟趋势、丢包、目标/实际速率、状态、各类预算、Pacer 队列和 QoE。

**实验覆盖：** 理想网络、RTT 变化、容量阶跃、突发丢包、反馈丢失、应用空闲、竞争流；比较收敛时间与过冲。

**最小验收：**

- 能区分 TWCC、REMB、CCFB 和 GCC 的层次与输入输出。
- 反馈暂停、应用空闲、CPU 受限时不误判网络过载。
- 固定容量阶跃实验能报告收敛时间、过冲、队列峰值和 QoE 变化。

对照 [[延迟趋势与过载检测]]、[[GCC 探测与码率控制状态机]]、[[WebRTC Stats]]。
