# 带宽估计

> [!tip] 阅读提示
> **前置：** [[RTCP]]、[[TWCC]]、[[延迟趋势与过载检测]]。
> **初读：** 读到「初读到此为止」就停。弄清：BWE 用反馈推断「这段时间大概能扛多少」，输出是带噪声的控制输入，不是线路真值。
> **深入：** 工程要点、误区表与验收清单，联调/排障时再读。

## 一句话说明

带宽估计（BWE）根据发送、到达和反馈信息推断当前路径在一段时间内可承载的媒体速率，为拥塞控制和码率分配提供参考。估计值是带有滞后、噪声和置信边界的控制输入，不是线路容量的永久真值。

## 先记住这三句

1. BWE = 从发送/到达/反馈推断路径**可承载媒体速率**，给拥塞控制当参考。
2. 估计值有滞后、噪声和置信边界；**不是**测速结果，也**不是**永久容量真值。
3. 低吞吐 ≠ 链路一定窄——先分清网络受限 vs 应用/CPU 受限（ALR）。

## 问题边界

- **上游：** [[RTCP]] / [[TWCC]] 反馈、发送历史、到达间隔、丢包窗口、Pacer 队列、应用产出。
- **下游：** 目标速率/上下限/状态 → [[拥塞控制]] / [[GCC]] → [[带宽分配]] → [[Pacing]]。
- **易混淆：**
  - BWE ≠ 测速（测速只描述收到多少；BWE 还要判断排队、丢包、反馈滞后、应用限制）。
  - REMB / TWCC / CCFB ≠ 同一个估计算法（它们是信号或反馈机制，估计策略在控制器中）。
  - 接收吞吐 ≠ 编码目标 ≠ BWE 输出。
  - 低吞吐 ≠ 一定链路容量低（可能应用受限或 CPU 不足）。
  - 延迟趋势细节见 [[延迟趋势与过载检测]]；GCC 闭环见 [[GCC]]，本篇不重复整套控制。

## 核心机制


### 观测信号

- 传输反馈提供到达间隔、丢包、接收速率和反馈覆盖范围；TWCC 使逐包时序更容易与发送历史对齐。
- 延迟趋势可以暴露排队增长，丢包控制可以在无法可靠获得时序时提供另一条约束；两者要考虑乱序、反馈延迟和应用受限。
- 发送队列、Pacer 等待时间、编码器实际产出和接收端吞吐用于判断“网络限制”还是“应用没有足够数据可发”。

### 端到端流程

1. 发送端把包序号、发送时间、大小和重传/探测标记写入历史；接收端记录到达时间、状态、接收字节和报告时间。
2. RTCP/TWCC 反馈把这些观测送回发送端，估计器按时间窗口配对发送与到达样本，过滤乱序、反馈延迟和无数据可发的区间。
3. 延迟趋势、接收吞吐和丢包控制分别给出容量/过载约束，估计器合并为目标速率、上限或状态。
4. GCC/应用层把目标速率传给编码器、分层选择和 Pacer；实际发送结果再回到下一轮估计。

```text
发送历史 + TWCC/RTCP
  -> 配对样本 / 过滤乱序与空闲窗
  -> 趋势 + 吞吐 + 丢包约束
  -> 目标 / 上限 / 增长|保持|下降
  -> 控制与发送 -> 新观测
```

### 计算示例

若一个统计窗口收到 100 个 1,000 字节包，窗口为 1 秒，接收速率约为 `100 × 1,000 × 8 = 800 kbit/s`。如果下一窗口只有 80 个包，下降可能来自网络丢失、发送码率变化、应用无数据或 Pacer 限制，必须结合发送历史和丢包状态判断。

若发送间隔为 10 ms、到达间隔为 25 ms，单个样本的相对排队增长约为 15 ms；连续多个包组的增长趋势才可用于过载判断，不能把一对时间差直接当作 BWE。

## 深入：输入输出表与工程

### 输入、状态与输出

| 类别 | 内容 |
| --- | --- |
| 输入 | 到达间隔差、接收速率、丢包窗口、RTT/报告时差、反馈新鲜度、Pacer 队列、应用产出 |
| 状态 | 发送历史、趋势滤波器、过载状态、目标/最小/最大速率、最近有效反馈时间 |
| 输出 | 控制参考：目标码率、安全上限或增长/保持/下降状态（非精确链路容量） |

估计应区分网络受限和应用受限：发送端没有编码数据或 CPU 不足时，低吞吐不能证明链路容量低。

## 工程要点

- 发送侧历史表要有容量和超时，记录项淘汰不能早于反馈覆盖窗口；重连时清理旧会话。
- 接收侧反馈应保留乱序窗口和缺失未决状态，不能把未收到的最新包立即计入永久丢失。
- 估计器需要限幅、平滑、滞回和最小/最大码率，避免无线抖动造成目标速率每个反馈周期剧烈跳变。
- 目标变化应通过统一控制接口传给编码器、分层器和 Pacer，并记录各模块是否实际接受该目标。
- 每轮估计都能追溯到反馈类型、样本窗口和有效时间；反馈年龄应对控制器可见。
- 目标速率、编码实际码率、线上速率和接收吞吐分别记录，勿混为同一曲线。

## 常见误区与故障

| 误区 / 故障 | 表现与排查 |
| --- | --- |
| BWE 就是测速 | 还需排队、丢包、反馈滞后、应用限制 |
| REMB/TWCC/CCFB=同一算法 | 它们是信号；估计策略在控制器 |
| 目标速率一直很低 | 查反馈过期、序号错配、趋势滤波、Pacer 积压 |
| 目标很高但实际发送很低 | 查编码器产出、应用受限、层选择、CPU |
| 单样本间隔差当容量 | 需连续趋势与窗口合并 |
| 空闲窗当弱网 | 应用无数据区间应过滤或标 ALR |

## 观测与验证

记录每轮估计的输入窗口、目标速率、实际发送速率、接收速率、丢包、RTT、趋势状态、反馈年龄和 Pacer 队列。

**场景：** 固定容量、突发带宽变化、反馈延迟、反馈丢失、乱序、应用空闲；验证估计是否稳定、收敛和可解释。

**最小验收：**

- 能用发送历史说明低吞吐是网络受限还是应用受限。
- 估计输出有上下限、平滑和反馈过期处理，不因单个异常样本失控。
- 四条曲线（目标 / 编码 / 线上 / 接收）分列记录。

**复盘问题：** 估计输出时间点是否早于当前发送决策？反馈年龄是否可见？同时间窗是否对齐发送历史、反馈、Pacer 与编码器产出？目标降低由延迟、丢包、吞吐还是应用受限触发？

对照 [[GCC]]、[[编码器与 BWE-Pacing 联动]]、[[WebRTC Stats]]。
