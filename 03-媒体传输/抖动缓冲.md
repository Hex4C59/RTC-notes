# 抖动缓冲

> [!tip] 阅读提示
> **前置：** [[RTP]]、[[播放截止时间]]。
> **初读：** 读到「初读到此为止」就停。弄清：它吸收抖动、稳住输出，不是越大越好。
> **深入：** 音视频差异、收缩策略与观测，排障时再读。

## 一句话说明

抖动缓冲在接收端暂存媒体包，吸收到达间隔波动，并按媒体时间线向解码器稳定输出。它同时承担乱序等待、去重、过期判断和欠载处理，不是越大越好的缓存；目标是让播放在可接受延迟内稳定。

## 先记住这三句

1. 抖动缓冲 = 接收端短暂停一下，把「忽快忽慢」的到达变成较稳的播放节奏。
2. 越大越能扛抖动，但交互会更「慢半拍」；目标深度是在延迟和连续性之间取舍。
3. 网络统计上的 jitter ≠ 缓冲目标大小；音频常必须按时出声，视频可以停一帧等参考。

## 核心机制

```text
收包 -> 有界缓冲：校验 / 扩展序号 / 去重 / 乱序记录
  -> 控制器：媒体时间 + 到达抖动 + 水位 + 播放目标
  -> 缺口：短等乱序/恢复，或触发 NACK（预算内）
  -> 超截止：late/drop -> PLC / 丢帧 / 错误处理
  -> 解码播放 -> 反馈欠载/积压/恢复给自适应控制
```

1. 收包线程按 SSRC/媒体线插入有界缓冲，执行长度校验、序号扩展、去重与乱序记录。  
2. 缓冲控制器根据媒体时间、到达抖动、欠载/过满与播放目标计算下一次取包时间。  
3. 对暂时缺口可短暂等待或触发恢复；超过播放截止则标记晚到并交给 PLC、丢帧或解码器错误处理。  
4. 解码与播放线程按媒体时间输出，持续把欠载、积压、丢弃与恢复结果反馈给自适应控制。

### 状态与边界

| 包状态 | 含义 |
| --- | --- |
| 未到 / 已收 / 重复 | 到达与去重 |
| 乱序等待 | 缺口短等中 |
| 已组帧 / 已解码 | 已向下游消费 |
| 已过期 | 超截止，记录原因后丢弃 |

缓冲上限应同时用包数、字节数与媒体时长约束，避免高码率视频把固定包数膨胀成很大内存。固定缓冲易于推理但不能适应突发；自适应缓冲要有增长/收缩速率与最小/最大时延边界。

## 时间与数值示例

若音频每 20 ms 一个包，初始缓冲目标为 60 ms，则至少要准备约 3 个可连续播放的包；若连续两个包晚到，剩余 20 ms 可能不足以等待一次 RTT。把目标从 60 ms 提到 120 ms 可提高抗抖，但会直接增加交互延迟，且不保证突发丢包能恢复。

```text
deadline = 计划播放时刻 - 解码/渲染安全余量
若 预计恢复到达 > deadline -> 不要空等，走 PLC/丢帧/刷新评估
```

播放边界：发现缺口时可短暂等待乱序或重传，但等待预算不能超过该媒体单元的播放截止。视频还要考虑帧内/帧间参考依赖；音频则可能在缺包时交给 PLC 或时域处理保持连续。过期包应记录原因并丢弃，不能继续挤占队列。详见 [[播放截止时间]]、[[丢包恢复策略]]。

## 问题边界

- **上游：** 解密后的 RTP（按 SSRC/媒体线）、到达时间、扩展序号、丢包恢复状态（NACK/RTX/FEC）、解码器需求。
- **下游：** 按媒体时间交给解码/播放；统计上的目标/实际延迟、late/drop、欠载、冻结；并影响 [[音视频同步]] 与 [[端到端延迟]]。
- **易混淆：**
  - RTP interarrival jitter（统计量）≠ 缓冲目标大小（播放策略）。
  - 缓冲越大 ≠ 越稳；过大掩盖发送/拥塞问题并增加交互延迟。
  - 网络丢包低 ≠ 听感/观感好；迟到丢弃、欠载、解码错误另算。
  - 音频与视频不能机械共用一套阈值：音频常必须出样本，视频可停一帧等参考。
  - [[NetEQ]] 是音频侧含 DSP 决策的实现；本篇谈通用接收缓冲职责，不展开 NetEQ 内部动作表。
## 工程要点

- **插入健壮性：** 支持乱序、重复与序号回绕；按时间戳组帧时不能假设一帧一个 RTP 包。
- **目标调节平滑：** 按缓冲趋势调整目标，而不是每个包到达都改目标，避免策略本身放大抖动。
- **错误回传：** 解码器缺参考或需刷新时，把状态传回恢复/[[PLI 与 FIR]] 路径，不能只把坏包留在缓冲里。
- **生命周期：** 关闭或切换媒体源时清空旧 SSRC 状态、取消播放定时器，防止旧回调访问失效缓冲。
- **音视频差异：** 音频以采样块与播放时钟为主；视频还需帧完整性与参考依赖。音频设备回调通常必须吐样本（见 [[NetEQ]]）。
- **收缩路径：** 网络恢复后要能回落目标延迟，否则交互会「一直拖」；收缩过猛又会造成新的欠载。

## 常见误区与故障表现

| 误区 | 故障表现 / 排查 |
| --- | --- |
| 缓冲越大越稳 | 延迟粘在高位；查收缩、过期丢弃、上游队列 |
| 把 jitter 统计当缓冲大小 | 调参无据；分清统计量与策略目标 |
| 网络恢复后延迟不回落 | 目标粘滞、时钟漂移、Pacer 堵塞 |
| 到达率正常仍卡顿 | 帧未组装完、解码耗时、参考帧、播放线程调度、欠载 |
| 音频套用视频「停一帧」 | 设备 underrun/爆音；音频更常必须出样本 |

## 观测与验证

**一起看：** 缓冲包数/字节/时长、目标与实际播放延迟、乱序等待、late/drop、欠载次数、恢复命中、解码耗时、冻结时长；对照 [[WebRTC Stats]] 与抓包时间线。

**实验覆盖：** 固定延迟、抖动突增、随机/突发丢包、带宽骤降、时钟偏差；弱网恢复后重点看目标是否回落。

**最小验收：**

- 固定 20 ms 音频帧：0/1/多个乱序与连续欠载。  
- 多包视频帧：帧未完整时不提前送解码器。  
- 改缓冲上限时同时报告延迟、冻结与 late/drop，不能只看卡顿。  
- 关闭、重连、SSRC 切换时定时器与旧包状态已清理。

复盘：缓冲目标按包数、字节、媒体时长还是播放时间定义，单位是否统一？late/drop、欠载、解码错误与网络丢失能否在统计中区分？
