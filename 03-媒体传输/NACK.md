# NACK

> [!tip] 阅读提示
> **前置：** [[RTP]]；承载见 [[RTCP]]。
> **初读：** 先读「一句话说明」「问题边界」「核心机制」和「截止时间示例」，弄清 NACK 是反馈请求、不等于必重传。
> **深入：** 状态字段、限流、与 RTX/关键帧分工在实现与排障时再读。

## 一句话说明

NACK（Negative Acknowledgement）是接收端依据 RTP 序号缺口发送的 RTCP 反馈，表示某些包暂时不可见并请求发送端检查是否可以重传。NACK 本身不携带媒体，也不等于发送端一定会重传——执行侧通常走 [[RTX]]，且受缓存、截止与预算约束。

## 问题边界

- **上游：** 扩展序号、乱序窗口、[[抖动缓冲]] 余量、播放截止、[[RTCP]] 反馈预算与调度。
- **下游：** 发送端重传缓存查询、RTX 生成、恢复后组帧；或转向 PLC/丢弃/视频刷新（[[PLI 与 FIR]]）。
- **易混淆：**
  - 序号缺口 ≠ 永久丢失；乱序晚到很常见，立即请求会制造伪缺口风暴。
  - NACK ≠ RTX：前者是 RTCP 反馈语义，后者是重传封装，可分别实现或组合。
  - NACK 计数高 ≠ 恢复率高；要看缓存命中与截止内到达。
  - fraction lost（RR）与「可 NACK 的缺口」口径不同，不能直接互替。
  - 视频缺参考时，单包重传可能已无意义，应评估关键帧刷新而不是堆叠 NACK。

## 核心机制

```text
收端：扩展序号 + 乱序窗口
  -> 缺口短等（抑制伪缺口）
  -> 仍缺且未过截止 -> 压缩进 NACK（RTCP）
  -> 发端：缓存？截止？预算？
       是 -> RTX 入 Pacer
       否 -> 拒绝 / 过期 / 转刷新
  -> 收端去重、还原序号、组帧或结束请求
```

1. 接收端按 RTP 序号维护扩展序号与乱序窗口，发现缺口先等待短窗口。  
2. 缺口仍未到且未超过播放截止，把缺失序号压缩进 NACK，经 RTCP 发送。  
3. 发送端查重传缓存，检查存在性、预计到达与重传预算，再决定是否生成 RTX。  
4. 收端收到原包或 RTX 后去重并恢复原序号空间；已过期或无法满足解码依赖的请求直接结束。

### 状态与字段

| 侧 | 关键状态 / 语义 |
| --- | --- |
| 接收 | 最高扩展序号、待确认缺口、首次发现时间、最后请求时间、请求次数 |
| 反馈 | “缺少哪些 RTP 序号”，不是“必须重传多少次” |
| 压缩 | 按实现支持的序号块格式打包，避免每缺口一包 RTCP |
| 发送 | 缓存覆盖 RTT+等待；时间窗、每包次数、总字节上限 |

RTT、抖动缓冲余量、解码依赖和当前 Pacer 队列共同决定重传价值。高丢包时一次性重传大量包会进一步推高队列，因此应有每次反馈与时间窗级别的重传限流。策略层汇总见 [[丢包恢复策略]]。

## 截止时间示例

假设收端在 45 ms 发现 101 号包缺失，计划 100 ms 播放，另留 5 ms 处理余量。若 RTT ≈ 20 ms，估计重传到达 `45 + 20 + 5 = 70 ms`，有限 RTX 仍有价值；若 RTT ≈ 80 ms，估计 130 ms，继续重传只增负载，应转向 PLC、丢弃或视频刷新。这是决策估算，不是成功保证。

```text
worth_rtx ≈ (now + RTT + process_margin) < play_deadline
```

更系统的截止模型见 [[播放截止时间]]；缓冲如何给等待预算见 [[抖动缓冲]]。

## 工程要点

- **乱序先于请求：** 收到更高序号后设等待计时器，不要立即为每个缺口发 NACK；同时限制反馈频率，防止反馈风暴吃掉 RTCP 预算。
- **发送限流：** 时间窗、每包次数、总字节上限；RTX 进入同一 Pacer 与 [[带宽分配]]，与新媒体公平竞争。
- **视频参考链：** 非参考包即使重传成功，也不一定值得延长整帧等待；参考链断裂且赶不上时评估 [[PLI 与 FIR]]。
- **独立测试面：** NACK 去重、序号回绕、SSRC 切换、缓存淘汰、反馈丢失、重复请求上限。
- **关联同一序号：** 把 NACK 包、RTX 包、恢复包与最终播放结果串在同一序号上排障，避免只看一侧计数。
- **SFU：** 下游 NACK 与上游缓存归属要清晰；无条件广播会把一个订阅端的缺口放大成全房间 RTX。

## 常见误区与故障表现

| 误区 | 故障表现 / 排查 |
| --- | --- |
| 见缺口就立刻 NACK | 伪缺口风暴、RTCP 带宽被打满 |
| 把 NACK 当 RTX | 协议路径理解错；分清反馈与封装 |
| 只看 NACK 数量 | 恢复率低；查缓存命中、RTT、截止、发送队列 |
| 恢复后重复解码 | OSN 还原、原包/RTX 去重、序号回绕比较 |
| 高丢包无限重传 | Pacer 队列推高；查限流与统一预算 |
| 可重传缺口误升关键帧 | 码率尖峰；先确认截止内 RTX 是否仍可能 |

## 观测与验证

**一起看：** NACK 发送时间、序号范围、重复次数、RTT；发送端缓存命中、RTX 字节、重传排队时延、过期请求原因；接收侧乱序等待命中率。对照 [[WebRTC Stats]] 与抓包。

**实验：** 固定 20 ms 音频帧或固定视频帧率，分别改变 RTT、随机丢包与突发丢包，比较恢复率、播放冻结与额外带宽；再加一组「反馈丢失」验证不会因重复 NACK 失控。

**最小验收：**

- 乱序、重复、序号回绕、反馈重复 → 不会无限 NACK。  
- 缓存命中、缓存淘汰、预计到达晚于截止 → 行为与原因码可解释。  
- 每个请求有原因、次数、字节成本与结束状态。  

复盘时优先问：缺口何时从「乱序未决」变成「可请求」？发送缓存命中率是否足以解释恢复率，而不是只看 NACK 数量？


## 与 FEC / 关键帧的分工（摘要）

NACK+RTX 适合可追回的个别缺口；保护窗口内的突发丢失更适合 [[FEC]]；参考链已断且截止内无法修包时升级为 [[PLI 与 FIR]]。不要把「NACK 计数上升」单独当成弱网结论——必须同时看命中率、过期率与播放结果（见 [[丢包恢复策略]]）。
