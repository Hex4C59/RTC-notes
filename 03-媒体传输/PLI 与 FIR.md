# PLI 与 FIR

PLI（Picture Loss Indication）和 FIR（Full Intra Request）都是 RTCP 反馈，用于请求视频发送端刷新解码参考。它们是恢复请求，不是对某个已丢 RTP 包的重传。

## 区别与使用

- PLI 表示接收端无法继续使用当前图片或参考链，通常由发送端决定何时产生适合业务的刷新帧。
- FIR 语义更强，带有命令序号，适合明确要求新的完整帧；发送端仍应抑制重复请求和控制关键帧频率。
- 关键帧可能造成短时码率峰值。请求前要检查当前参考链、播放截止、Pacer 队列和多订阅者影响；SFU 不能把每个下游请求无条件放大成一次全局刷新。

## 端到端流程

1. 接收端检测到参考帧损坏、关键图片缺失或解码器无法继续，先确认单包重传是否仍有意义。
2. 若无法通过 NACK/RTX 在播放截止前修复，则产生 PLI 或 FIR，并按反馈抑制窗口合并重复请求。
3. 发送端或 SFU 决定刷新范围、关键帧类型和发送时间，编码器生成新的独立解码起点。
4. 新帧经过分片、Pacer 和拥塞控制发送；接收端收到参数集和关键帧后重置参考状态，恢复正常解码。

## 语义与状态

- PLI 表示当前图片或参考链不可用，通常允许发送端根据编码状态安排刷新，不携带“重传哪个 RTP 序号”的要求。
- FIR 的请求序号用于识别新的刷新命令并抑制重复处理；它适合明确要求完整刷新，但不意味着发送端可以忽略速率和队列。
- 接收端应维护最近请求时间、请求来源、当前解码参考、等待的关键帧和恢复超时；同一故障不能被每个下游包重复放大。
- 关键帧及其参数集的 RTP 时间戳、SSRC 和协商编码必须与原媒体线一致，或由转发层显式建立新映射。

## 数值与取舍示例

若一个关键帧约 300 KB，目标发送速率约 10 Mbit/s，单纯串行发送所需时间约为 `300 × 1024 × 8 / 10,000,000 ≈ 246 ms`，还未计入其他流量和排队。因此刷新请求可能短时挤占音频或推高 Pacer 队列，不能在每个下游都立刻触发全量关键帧。

## 发送侧与接收侧实现

- 接收侧在发起刷新前应带上可诊断原因，例如参考帧缺失、解码器错误或加入新层，并设置最小请求间隔。
- 发送侧应把关键帧成本交给带宽分配和 Pacer，必要时采用受限刷新、逐步 intra refresh 或等待更合适的编码边界。
- SFU 应按发布流、订阅层和下游状态聚合请求；下游的 PLI 不应无条件广播给所有观看者。
- 关键帧到达后要检查 SPS/PPS 或等价参数是否可用、帧组装是否完整以及解码器是否真正恢复。

## 常见误区与故障表现

- 误区：PLI/FIR 是 NACK 的另一种写法。它们请求刷新参考，不会找回指定丢包。
- 误区：收到 PLI 就马上发送超大关键帧。高并发时会形成关键帧风暴和新的丢包。
- 故障：PLI/FIR 频繁循环，检查关键帧是否完整、参数集是否丢失、解码器参考状态是否正确重置。
- 故障：关键帧已发送但画面仍黑，检查 PT/SSRC/RID 映射、分片重组、解码器错误和关键帧前的参数集。

## 观测与实验

记录 PLI/FIR 计数、请求间隔、请求原因、关键帧大小、发送耗时、Pacer 排队、恢复首帧时间和刷新后的冻结率。用“单个接收端参考帧丢失”“多个订阅端同时请求”“带宽骤降”三个场景验证限流和聚合行为。

## 最小验收清单

- 能区分参考包缺失、解码器错误和加入新层三类刷新原因。
- 对同一故障连续触发 PLI/FIR 时，请求应合并或受限，而不是形成反馈风暴。
- 关键帧发送后要验证参数集、完整帧、解码参考和首帧时间。
- 多订阅端测试中，单个下游请求不应无条件放大为所有流同时刷新。

## 复盘问题

- 触发刷新前是否确认单包恢复已经来不及，还是误把可重传缺口升级为关键帧？
- 请求是否按发布流、订阅层和下游聚合，是否有最小间隔和退避？
- 关键帧的大小、发送时间和恢复首帧是否回到同一条诊断链？
- 刷新后仍黑屏时，能否区分参数集、分片、参考链和渲染故障？

补充核对：刷新请求的产生端、聚合端和执行端可能不同，日志必须记录每一跳的请求 ID 与节流结果。
关键帧请求的成功标准是恢复可解码播放，而不是仅看到发送端生成了一个关键帧。
