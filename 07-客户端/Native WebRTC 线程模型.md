# Native WebRTC 线程模型

## 一句话说明

Native WebRTC 把信令、网络和工作负载分配到具有明确线程归属的任务队列；对象创建、调用和销毁必须遵守其序列约束，不能把异步回调当作任意线程函数。

## 核心机制

- 信令序列维护 PeerConnection 与协商状态，网络序列处理传输，工作序列承担媒体与编解码任务；具体划分随版本演进。
- 跨序列操作通过任务投递和回调完成，引用寿命必须覆盖异步执行窗口。
- 停止流程需要阻止新任务、取消或排空在途任务，再按依赖逆序释放对象。

## 线程、序列与任务队列

WebRTC Native 更强调“在哪个序列上访问对象”，而不是要求每类工作永久绑定某个操作系统线程。一个 TaskQueue 可以由线程池调度，但同一序列中的任务仍按约束执行。因此阅读源码时要区分：

- 线程：操作系统调度和阻塞的执行实体。
- 序列：要求任务串行、维持对象不变量的逻辑上下文。
- 任务队列：投递异步工作和延迟任务的接口。
- 实时媒体回调：有严格截止时间，不能因为业务锁或 I/O 阻塞。

具体类名、默认队列数和哪些对象在哪个队列上会随 WebRTC 提交变化。稳定的判断依据是接口注释、`SequenceChecker`/线程检查和对象构造处，而不是旧文章中的固定三线程图。

## 常见数据流

1. 业务层在信令序列创建或操作 PeerConnection，发起 SDP/Track 变更。
2. 传输配置异步送到网络序列，套接字事件和 RTP/RTCP 在这里推进。
3. 编解码、音频处理和部分媒体转换在工作序列或专用队列运行。
4. 结果通过任务或 observer 回到约定序列，再更新业务状态。

回调发生在哪个序列必须查当前接口契约。即使回调今天恰好来自信令线程，也不应在没有契约保证时把它当成永久行为。

## 对象所有权与异步寿命

- 原始指针被任务捕获后，任务执行前对象可能已经销毁；应使用项目约定的引用、弱引用或 pending-task 安全机制。
- 引用计数只能保证对象仍存在，不能自动保证在正确序列访问。
- 回调向业务层传递 buffer 时，要明确共享引用、只读期限和是否允许跨线程保存。
- 周期引用会让 PeerConnection 关闭后对象仍存活，表现为设备、线程或网络资源不释放。

关闭的核心不是“调用一次 Close”，而是建立屏障：停止产生新工作，断开外部回调，取消或让在途任务完成，再按依赖逆序释放传输、媒体和工厂对象。

## 工程要点

- 为每个接口记录允许调用的线程/序列，并在调试构建中使用序列检查。
- 回调不得阻塞实时路径；耗时 I/O 和业务逻辑应转移到独立队列。
- 源码阅读必须固定 WebRTC 提交，不依赖旧书中的 VoiceEngine、VideoEngine 或 GYP 目录。

## 死锁和实时性风险

- 在序列 A 持锁并同步等待序列 B，而 B 的任务又回调 A，会形成经典环形等待。
- 把设备回调同步转发到 UI 线程，会把界面卡顿传播到音频欠载或视频丢帧。
- 实时线程频繁分配、大量格式化日志或执行磁盘访问，会制造周期性抖动。
- 关闭时用“睡眠一段时间再释放”隐藏竞态，无法证明在途任务已经结束。

跨序列设计优先传递不可变快照或独占消息，缩小共享锁范围。必须同步等待时，要画出等待方向并确认不存在反向调用。

## 诊断方法

- 记录任务队列名、对象 ID、事件和单调时间，重建跨序列因果关系。
- 在调试构建启用序列检查、线程注解和竞态检测能力；触发错误时保留完整创建与销毁栈。
- 关注回调耗时分布、队列排队时间、音频 underrun、视频 dropped frame 和关闭超时。
- 对偶发 use-after-free，优先检查任务捕获和 observer 注销顺序，而不是仅在崩溃点加锁。

## 关闭流程示例

一个稳健顺序可以是：业务状态进入 closing，拒绝新协商；停止采集与发布；注销会继续产生任务的 observer；关闭 PeerConnection 和传输；等待约定的关闭回调或队列屏障；最后释放工厂、设备与队列。实际 API 以所用版本为准，但“停止源头 → 截断回调 → 排空依赖 → 释放所有者”的原则稳定。
