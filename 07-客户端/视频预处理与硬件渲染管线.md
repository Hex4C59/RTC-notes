# 视频预处理与硬件渲染管线

> [!tip] 阅读提示
> **前置：** 无强前置；可先从本篇一句话说明读起。
> **初读：** 先读「一句话说明」和「帧描述必须完整」，弄清 视频预处理与硬件渲染管线 解决什么问题、不负责什么。
> **深入：** 「内容适配状态机」、「可观测指标」、「故障注入与验收」 在实现、联调或排障时再读。

## 一句话说明

视频 RTC 链路经常在摄像头、GPU、硬件编码器、硬件解码器和显示合成器之间传递 surface。真正的低延迟不只取决于编码耗时，还取决于格式转换、复制、同步栅栏、队列深度和表面生命周期。

## 帧描述必须完整

一个视频帧至少要携带：宽高、像素格式、plane 地址或纹理句柄、stride、色彩空间、色彩范围、传递函数、旋转/镜像、捕获时间、设备代次和 buffer 所有权。只有 `width × height × 3/2` 不能安全描述带对齐 stride 的 I420/NV12。

## 发送端处理路径

```text
Camera/Screen surface
  -> 等待生产者 fence
  -> 裁剪/旋转/缩放/色彩转换
  -> 内容适配（帧率、分辨率）
  -> Encoder input surface 或 CPU buffer
  -> 硬件编码队列
```

摄像头输出可能是 NV12、YUV_420_888、CVPixelBuffer、D3D texture 或 EGL texture。若编码器接受同类共享表面，可避免 CPU 往返；格式、设备或 API 不兼容时仍需显式复制和同步。

## 内容适配状态机

适配器根据编码预算、CPU/GPU 负载和内容变化选择输出尺寸与帧率：

```text
Stable
  ├─ 带宽/CPU 过载持续 -> Downscale 或 DropRate
  ├─ 资源恢复并超过滞回 -> Upscale
  └─ 设备/方向变化 -> Reconfigure
```

升降级要有滞回和最小保持时间，避免在阈值附近来回改变分辨率。丢帧必须发生在编码前并保留时间线，不能通过篡改捕获时间制造“恒定帧率”。

## GPU 同步和所有权

- producer fence 表示写入完成，consumer fence 表示使用完成；只传纹理句柄而不传同步关系会读到半帧或复用中的内存。
- 引用计数保证对象存在，不一定保证 GPU 工作已经完成。surface 池只有在消费者 fence 完成后才能回收。
- 跨图形 API 或跨设备共享可能触发隐式复制；应通过 trace 和 GPU 工具验证，不能根据 API 名称宣称零拷贝。
- 屏幕共享纹理可能受权限和受保护内容约束，失败应形成显式黑帧/停止状态而非沿用上一帧。

## 硬件编码/解码队列

硬件 codec 通常是异步状态机：配置、排队输入、等待输出、格式变化、flush、重建和关闭。输入返回成功只表示进入驱动队列，不代表编码完成；解码输出 surface 也可能继续被渲染器占用。

```text
Unconfigured -> Configured -> Running
Running -> Draining/Flushing -> Running
Running -> Reconfiguring -> WaitingForKeyframe -> Running
任意状态 -> Error -> Recreate
任意状态 -> Closing -> Closed
```

分辨率、profile、颜色格式或 surface 变化可能要求重建。重建后解码器必须等待参数集和可解码刷新帧，旧代次输出即使晚到也不能交给新渲染管线。

## 接收端呈现路径

```text
Decoder output surface
  -> 等待解码完成 fence
  -> 色彩转换/缩放/旋转
  -> 按 A/V 计划时间排队
  -> 图形合成器
  -> VSync latch
  -> 屏幕扫描显示
```

“提交 draw”不是实际呈现。帧可能错过当前 VSync，再多等一个刷新周期；系统合成器还可能三缓冲。若视频落后主时钟，应该丢弃可安全丢弃的旧帧，而不是把队列完整播放造成延迟不断增加。

## 队列与背压

采集、处理、编码输入、编码输出、网络、解码输入、解码输出和渲染各自都可能排队。每个队列必须定义最大帧数、最大媒体时长、过期规则和丢弃责任。

实时视频一般优先保留最新可解码状态；但不能随意丢参考帧或参数集。硬件 surface 池耗尽时，应定位哪个消费者未释放，不能只扩大池掩盖生命周期泄漏。

## 颜色和几何正确性

- NV12/I420 的 UV 顺序、plane stride 和裁剪偶数边界错误会造成绿屏或偏色。
- BT.601/BT.709/BT.2020、limited/full range 和 HDR transfer 解释错误会造成灰雾、过黑或色偏。
- 旋转既可修改像素，也可用元数据表达；只能选一种权威语义，避免重复旋转。
- 本地预览可能走另一条处理路径，预览正常不能证明编码器输入正确。

## 线程和关闭顺序

摄像头回调、GPU context、codec 回调和 UI/渲染线程有各自亲和性。关闭时先停止新帧，再取消回调或建立代次屏障，等待 GPU/codec 在途工作完成，最后释放 surface、context 和设备。靠固定 sleep 等待无法证明资源已停止使用。

## 可观测指标

为每帧关联 capture ID，记录采集、预处理开始/结束、编码入队/输出、解码入队/输出、渲染提交和实际呈现时间。同步记录各队列时长、拷贝字节、格式转换、GPU fence 等待、surface 池占用、过期丢帧和 VSync miss。

## 故障注入与验收

1. 改变 stride、色彩范围、旋转和分辨率，验证格式描述全链路传播。
2. 延迟 GPU fence 或占满 surface 池，确认背压有界且不会使用已回收表面。
3. 模拟硬件 codec 错误、flush 和重建，确认旧代次回调被拒绝并等待新关键帧。
4. 人为降低渲染线程速度，确认旧帧被按策略丢弃且延迟能回落。
5. 使用 LED/屏幕光学回环测量到实际显示，而不以解码回调作为终点。

## 常见误区

- 硬件编解码一定更低延迟：驱动队列和格式复制可能抵消计算收益。
- 共享纹理句柄就是零拷贝：仍可能存在隐式复制和同步等待。
- 解码输出即用户看到画面：还要经过调度、GPU 合成和显示刷新。
- 队列加大能解决卡顿：它通常把卡顿转换成更高交互延迟。
