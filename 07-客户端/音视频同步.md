# 音视频同步

## 一句话说明

音视频同步先把不同 RTP 时钟域映射到共同参考时间，再依据本地播放主时钟安排呈现，使同一事件的声音和画面保持在可接受偏差内。

## 核心机制

- RTCP Sender Report 提供每条流的 RTP/NTP 对，接收端据此建立跨流时间映射。
- 播放器通常让连续性要求更强的音频作为主时钟，视频通过等待、追赶或丢帧逐步校正。
- 长时间通话需要估计时钟频偏；一次对齐不能消除设备时钟持续漂移。

## 为什么不能直接比较 RTP 时间戳

音频常以采样率作为 RTP 时钟频率，视频常使用 90 kHz 时钟；两条流的初始时间戳又通常是随机值。因此 `audioTimestamp - videoTimestamp` 没有物理意义。接收端需要把各自的 RTP 时间戳先映射到共同参考时间。

RTCP Sender Report 提供一对观测：

```text
(某个 RTP timestamp, 与之对应的 NTP wall-clock time)
```

对同一 SSRC 收到多个有效映射后，可以估计该 RTP 时钟相对于共同时间的偏移和频率。同步逻辑随后得到每个音频块和视频帧的相对采集/发送时间。

Sender Report 不足或跳变时，接收端可能使用到达时间和本地估计暂时维持播放，但精度与稳定性会下降。SSRC 切换、重启和时间戳回绕都需要新代次处理。

## 播放调度

1. 抖动缓冲决定媒体数据何时具备可播放条件。
2. 解码器输出帧及其媒体时间。
3. 同步控制计算相对于主时钟的目标呈现时间。
4. 音频按设备节奏连续播放；视频可等待、立即显示或丢弃过晚帧。
5. 控制器以小步调整延迟，避免用户感知到突然跳变。

音频常作为主时钟，因为音频断裂和变速更敏感，且播放设备持续消耗样本；但具体策略取决于播放器、内容和平台，并非协议强制。

## 同步误差

可以定义 `A/V offset = 视频实际呈现时间 - 对应音频实际播放时间`。正负号必须在监控中明确。这个偏差包含网络抖动缓冲、解码排队、渲染队列和设备输出延迟，不能只从 RTP 时间戳推导。

校正通常设置容忍死区：小偏差不动作，持续偏差逐步调整，超出硬阈值时才丢帧或重置。阈值应通过产品体验测试确定，而不是从单一通用数字照搬。

## 工程要点

- 不可直接比较音频和视频的 RTP 时间戳数值，它们通常使用不同频率和随机起点。
- 校正要设置死区和最大步长，避免画面跳动或音频突变。
- 分别记录捕获时间、解码完成时间、计划播放时间和实际呈现时间。

## 时钟漂移

发送采集设备、接收音频设备和系统单调时钟都可能有 ppm 级频偏。即使开始时完全对齐，几十分钟后也会积累可见偏差。音频侧常通过极小的时域伸缩或重采样补偿漂移，视频侧通过调度和偶发丢帧配合。

如果偏差呈线性增长，优先怀疑时钟频率估计或设备漂移；如果在网络抖动时突变，优先检查缓冲目标和时间映射重置。

## 常见故障

- 开始同步、随后逐渐口型不一致：时钟漂移未补偿或使用错误时钟频率。
- 每次切换视频层后跳动：新层时间戳/SSRC 映射与旧输出时间线未衔接。
- 网络恢复后长期不同步：音频和视频缓冲恢复策略不同，积压未按统一目标排空。
- 统计显示同步正常但主观异常：实际显示器/音频设备延迟没有纳入测量。

## 验证方法

- 使用同时产生声响和视觉闪烁的测试素材，从实际扬声器与显示器端测量，而非只看内部计划时间。
- 注入上下行抖动、丢包和带宽变化，观察偏差能否回到死区，并记录恢复时间。
- 对长通话绘制 A/V offset、两侧 jitter buffer、解码队列和音频伸缩随时间的趋势。
- 对 SSRC 切换、暂停恢复、设备切换和后台前台切换分别验证时间线代次。
