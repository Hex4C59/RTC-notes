# NetEQ

## 一句话说明

NetEQ 是 WebRTC 接收端的自适应音频抖动缓冲与丢包隐藏模块，在网络到达节奏和固定音频播放节奏之间选择正常解码、PLC、加速、扩展或合并输出。

## 核心机制

- 插入侧按 RTP 序列与时间戳整理包，播放侧按设备周期请求固定数量的音频样本。
- 延迟管理器结合到达间隔、缓冲水平和时钟漂移选择目标延迟。
- 决策逻辑根据包是否到达及缓冲状态选择解码、PLC、时域加速/扩展或从隐藏音频平滑回归真实音频。

## 输入与输出节奏

网络侧按不规则间隔把 RTP 包送入 NetEQ；音频设备则通常每隔固定周期索取固定数量的 PCM 样本。这两个节奏之间的差异就是抖动缓冲需要吸收的对象。

插入时需要处理：

- RTP 序列号回绕、乱序、重复和迟到。
- 时间戳对应的采样位置、Payload Type 与解码器配置。
- RED、DTMF、舒适噪声等非普通语音负载的语义。
- 包持续时间变化以及网络和发送设备时钟的偏差。

拉取时必须在截止时间输出音频。缺少当前包时，系统不能无限等待网络，只能根据缓冲、解码器和历史信号选择替代策略。

## 典型输出动作

| 动作 | 使用条件 | 主要代价 |
| --- | --- | --- |
| 正常解码 | 下一个可播放包已到达 | 保持原始内容与节奏 |
| PLC/扩展 | 当前包缺失且不能再等 | 内容是估计，连续使用会劣化 |
| 加速 | 缓冲过深或本地播放偏慢 | 缩短音频但可能引入听感变化 |
| 预扩展 | 缓冲过浅或需要拉长 | 增加延迟稳定性但改变时域 |
| 合并 | 从 PLC 平滑回到真实包 | 减少边界突变 |

动作名称和内部算法随实现版本变化，但目标始终是在连续性、延迟与信号失真之间权衡。

## 目标延迟

目标延迟不是越低越好。过低会让轻微抖动就变成迟到丢弃或 PLC；过高则直接增加交互延迟。延迟管理会参考到达间隔分布、当前缓冲、丢包模式和时钟漂移，并以受控速度调整，避免目标值抖动。

应用设置的最小/最大延迟、设备缓冲和系统音频栈也会影响最终延迟。只看 NetEQ 内部缓冲无法得到完整的端到端播放延迟。

## 工程要点

- NetEQ 不只是一个按序容器；它同时管理播放截止、解码器状态和信号连续性。
- 评价要同时看延迟、晚到丢弃、隐藏比例、加速/扩展次数和主观听感。
- 不把旧论文中的模式或类名直接等同当前 WebRTC 实现，源码结论需固定版本。

## 与 Opus 恢复能力的关系

Opus 解码器可以提供 PLC，并可能使用带内 FEC 恢复前一帧。是否等待 FEC 要结合包时长和播放截止：等待下一包才能恢复前一包，等得过久就会增加延迟。NetEQ 负责在可用包、解码器能力与当前截止之间做调度，编解码器只提供可选恢复工具。

## 常见问题

- 声音连续但延迟越来越高：目标延迟或上游队列持续增大，恢复后未及时排空。
- 周期性机械音：连续 PLC、时钟漂移或错误的包时长/时间戳解释。
- 网络恢复后爆音：从隐藏音频回归真实音频时缺少平滑，或时间线发生跳变。
- Stats 丢包不高但听感差：可能是包迟到、设备欠载、解码错误或频繁时域调整。

## 观测指标

应联合观察接收包数、网络丢包、迟到丢弃、当前/目标抖动缓冲延迟、解码样本数、concealed samples、silent concealed samples、加速/扩展次数及音频设备 underrun。字段名称以当前 WebRTC Stats 和实现版本为准。

一个有效实验是注入固定 50 ms 基础延迟，再逐步增加 0–80 ms 抖动和突发丢包，同时画出目标缓冲、实际缓冲、PLC 比例与端到端延迟。这样能区分“缓冲吸收抖动”和“延迟失控”。
