# NetEQ

> [!tip] 阅读提示
> **前置：** [[抖动缓冲]]、[[播放截止时间]]、[[Opus]]；时钟概念见 [[时钟与时间戳]]。
> **初读：** 读到「初读到此为止」就停。弄清：NetEQ 用「设备拉样本」驱动——在不规则到达与固定出声之间做解码/PLC/加速等取舍。
> **深入：** 与 Opus FEC 分工、状态机与实验方法，排障时再读。

## 一句话说明

NetEQ 是 WebRTC 接收端的自适应**音频**抖动缓冲与丢包隐藏模块。它在不规则的网络到达节奏与设备固定拉流节奏之间，选择正常解码、PLC、加速、扩展或合并输出。它不是视频组帧缓冲，也不负责 AEC/NS 等发送前处理。

## 先记住这三句

1. NetEQ = 自适应**音频**抖动缓冲 + 丢包隐藏；不是视频组帧，也不做 AEC/NS。
2. 设备回调到点必须吐样本——不能为等「完美包」无限阻塞（视频可以停，音频常不行）。
3. 目标延迟不是越低越好：太低就狂 PLC，太高交互拖；网络丢包低 ≠ 听感一定好。

## 问题边界

- **上游：** 解密后的音频 RTP（含 RED/DTMF/CN 等）、载荷类型与解码器、到达时间。
- **下游：** 固定时长的 PCM 块交给播放图；统计（隐藏比例、加速/扩展、当前/目标延迟）。
- **易混淆：**
  - NetEQ ⊂ 广义的音频 [[抖动缓冲]] 实现，但还包含 DSP 决策与解码器调度。
  - Stats 里网络丢包低 ≠ 听感好；迟到丢弃、隐藏、设备欠载另算。
  - Opus 带内 FEC/PLC 是工具；**是否等待、是否使用**由 NetEQ 结合截止时间决定。

## 核心机制

1. **Insert：** 按扩展序号/时间戳放入有界缓冲，处理乱序、重复、迟到。
2. **Delay manager：** 根据到达间隔、缓冲水位、漂移估计目标延迟。
3. **GetAudio：** 设备周期到点必须产出样本；缺包则走 PLC/加速/扩展等。
4. **Decode / DSP：** 调用解码器或时域处理，维护连续性与解码器状态。

```text
RTP arrive -> Insert/Reorder
Device callback -> GetAudio(need N samples)
                 -> decision: decode | PLC | accelerate | expand | merge
                 -> PCM out
```

## 输入与输出节奏

网络侧间隔不规则；音频设备通常每隔 10/20 ms 索取固定样本数（例如 48 kHz 下 20 ms = 960 样本/声道）。差异就是缓冲要吸收的对象。

Insert 需处理：序号回绕、乱序、重复、迟到；时间戳与 PT；RED/DTMF/CN；包时长变化与时钟偏差。

GetAudio 必须在截止前输出。不能为了“等一个完美包”无限阻塞设备回调。

## 典型输出动作

| 动作 | 使用条件 | 主要代价 |
| --- | --- | --- |
| 正常解码 | 下一可播包已到 | 保持内容与节奏 |
| PLC / expand | 包缺失且不能再等 | 估计信号，连用劣化 |
| accelerate | 缓冲过深或播放偏慢 | 听感变速/伪影 |
| preemptive expand | 缓冲偏浅，提前拉长 | 增稳但改时域 |
| merge | 从 PLC 回到真包 | 减少边界突变 |

名称与内部算法随 WebRTC 版本变化；目标始终是连续性、延迟、失真的权衡。

## 目标延迟

目标延迟不是越低越好。过低：轻微抖动就 PLC；过高：交互变拖。

延迟管理参考：到达间隔分布、当前缓冲、丢包模式、时钟漂移；并以受控速度调节，避免目标值抖动。

应用设置的 min/max delay、设备缓冲、系统音频栈都会叠到端到端延迟上——只看 NetEQ 内部缓冲会低估。关系见 [[端到端延迟]]。

### 水位示意

```text
underflow 区 |  目标带  |  overflow 区
   PLC↑     | 正常解码 |  加速↑、延迟↑
```

## 具体例子

20 ms 帧，目标缓冲 60 ms（约 3 包）。连续两包晚到，剩余可等待窗口可能 &lt; 一次 RTT。此时对第三包空等 RTX 不如 PLC 顶过去；若强行等到 RTX，播放会整体后移，用户感觉“突然变慢半拍”。把目标提到 120 ms 能抗抖，但稳态交互延迟也加 60 ms。

## 决策与截止时间

结合 [[播放截止时间]]：

```text
若下一包预计到达 > 播放截止:
    不要空等 -> PLC/expand 或跳过
否则:
    可短暂等待乱序/RTX/FEC
```

等待预算吃光后还死等，只会把抖动变成确定卡顿。视频可以停一帧；音频设备通常必须吐样本，否则 underrun 爆音。

## 与 Opus 恢复能力的关系

- Opus 可 PLC，也可能用带内 FEC 恢复**前一帧**（常依赖下一包）。
- 等下一包换 FEC：可能多等一个帧长，直接顶延迟预算。
- NetEQ 负责在“可用包 / 解码器能力 / 当前截止”之间调度；编解码器只提供可选工具。
- 不要把 “Opus FEC on” 理解成 NetEQ 可以无缓冲。

## 生命周期与重置

```text
Created -> Running -> Flushing -> Running
Running -> CodecChange -> Running
任意 -> Closed
```

- SSRC/PT 切换、流重启：flush 旧包与 DSP 状态，防止旧语音拼进新流。
- 设备采样率变化：重配解码与缓冲换算。
- 长时间 mute 后恢复：注意目标延迟是否粘在高位。

## 工程要点

- NetEQ 不只是按序容器；它管截止、解码器状态和信号连续。
- 回调里不做重活；预分配、限制锁范围。
- 评价同时看：延迟、晚到丢弃、隐藏比例、加速/扩展次数、主观听感。
- 不把旧论文类名直接映射到当前实现；源码结论钉死 revision。
- 与 [[音视频同步]]：音频主时钟时，NetEQ 输出节奏会影响视频等待。

## 常见误区与故障表现

- **声音连续但越来越拖：** 目标延迟或上游队列增大后未收缩。
- **周期性机械音：** 连续 PLC、漂移处理不当、包时长/时间戳解错。
- **网络恢复后爆音：** PLC→真包缺 merge，或时间线跳变。
- **Stats 丢包不高但难听：** 迟到丢弃、设备欠载、解码错、频繁时域拉伸。
- **把视频卡顿策略套音频：** 音频更常“必须出样本”。

## 观测与验证

**建议一起看：** 接收包、网络丢包、迟到丢弃、current/target jitter buffer delay、解码样本、concealed / silent concealed、accelerate/expand 次数、device underrun。字段名以当前 WebRTC Stats 为准（见 [[WebRTC Stats]]）。

**可重复实验：**

1. 固定 50 ms 基础延迟，叠加 0–80 ms 抖动  
2. 随机丢包 vs 突发丢包  
3. 开关 Opus FEC，比较延迟与隐藏比例  
4. 人为制造 +100 ppm 时钟偏  
5. 弱网恢复后观察目标延迟是否回落  

画出：目标缓冲、实际缓冲、PLC 比例、端到端音频延迟——区分“缓冲吸收抖动”与“延迟失控”。
