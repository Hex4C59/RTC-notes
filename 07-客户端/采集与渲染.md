# 采集与渲染

## 一句话说明

采集把麦克风、摄像头或屏幕转换为带格式和时间信息的媒体帧；渲染把解码结果按设备节奏输出，并处理权限、设备变化和实时线程边界。

## 核心机制

- 设备枚举和约束决定输入格式，媒体轨道控制内容是否持续产生及发送。
- 音频设备通常按固定周期拉取或推送样本，视频设备按帧产生并可能动态改变分辨率或方向。
- 渲染侧根据播放时钟调度画面并持续输出音频，欠载、阻塞或格式转换都会影响体验。

## 采集生命周期

1. 枚举设备并获取权限；设备列表在授权前后可能暴露不同信息。
2. 根据产品意图请求分辨率、帧率、采样率、声道等约束。
3. 系统选择实际设备格式，应用必须读取最终 settings，而非假设约束一定精确满足。
4. 每个采集块附带格式、时间和旋转/色彩等元数据，进入处理与编码链路。
5. 设备切换、权限撤销、系统中断或轨道停止触发明确状态迁移和资源释放。

浏览器的 `enabled=false`、`muted`、`ended` 与“业务静音”含义不同。Native SDK 也可能区分关闭发送、停止 source 和销毁设备；产品状态必须映射到真实媒体状态。

## 音频采集与播放

- 设备通常按固定时长回调交错或平面 PCM，必须明确采样率、声道、样本格式和帧数。
- 采集时间用于端到端延迟与同步；用回调到达时间替代硬件采集时间会引入队列误差。
- AEC 需要与麦克风输入时间对齐的远端播放参考；参考缺失、音量链路不一致或额外延迟会降低消除效果。
- 播放设备要求持续供给数据。业务锁、日志、GC 或重采样阻塞会导致 underrun，即使网络完全正常也会听到断续。

## 视频采集与渲染

- 视频 buffer 除宽高外还有像素格式、plane、stride、色彩范围、色彩空间和旋转信息。
- 摄像头可能动态降帧或改变曝光；屏幕共享帧率低但局部变化锐利，对编码策略不同。
- 零拷贝纹理和硬件 buffer 有线程与生命周期约束；渲染前失效会出现绿屏、花屏或偶发崩溃。
- 渲染应按计划呈现时间决定等待或丢帧，不能简单“解码完立刻画”，否则音画同步和抖动会恶化。

## 工程要点

- 明确回调线程、缓冲所有权、设备热插拔和权限撤销后的状态转换。
- 音频播放参考应回送给回声消除；视频旋转、色彩信息和 stride 不能靠尺寸猜测。
- 实时回调内避免阻塞、日志洪泛和无界分配。

## 格式协商与转换

采集设备支持的格式、编码器输入格式和渲染器格式经常不同。转换应集中在明确边界，并记录转换成本。例如摄像头输出 NV12、软件编码器需要 I420 时，需要考虑色度布局、stride 和拷贝；音频从 48 kHz 双声道转换到算法要求的块大小时，要保持连续时间线。

避免每个模块各自猜测格式并重复转换。稳定接口应携带显式描述和 buffer 所有权，并在分辨率或设备切换时原子更新。

## 常见故障与观测

| 现象 | 重点检查 |
| --- | --- |
| 本地预览正常、远端黑屏 | 编码输入、轨道发送状态、协商方向 |
| 远端画面旋转或颜色错误 | rotation、stride、色彩范围/矩阵、plane 顺序 |
| 音频周期性爆音 | 设备 underrun、块大小、重采样连续性、实时线程阻塞 |
| 切换设备后无声 | 新设备启动状态、旧回调代次、轨道是否仍绑定 source |
| 后台回来延迟很高 | 设备恢复、积压队列、旧时间戳和关键帧请求 |

至少记录实际采集格式、采集帧率、设备回调间隔、转换耗时、编码队列、渲染丢帧、音频 underrun 和设备状态事件。测量时把采集时间、进入编码时间、解码完成与实际呈现时间分开。

## 场景示例

手机旋转后，相机仍输出横向 buffer，但元数据的 rotation 改变。若预处理阶段已经物理旋转像素，后续又按元数据再旋转一次，远端会看到错误方向。正确做法是约定“像素已旋转”或“由元数据描述旋转”中的一种，并在编码和渲染边界保持一致。
