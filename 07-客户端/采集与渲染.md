# 采集与渲染

> [!tip] 阅读提示
> **前置：** [[PCM 与采样]]、[[YCbCr 与色度抽样]]；路由见 [[音频路由与设备热插拔]]。
> **初读：** 读到「初读到此为止」就停。弄清：采集→带格式/时间的帧，渲染→按设备节奏出；本地预览好 ≠ 远端能收到。
> **深入：** 格式转换边界、线程所有权与故障表，联调时再读。

## 一句话说明

采集把麦克风、摄像头或屏幕转成带格式与时间信息的媒体帧；渲染把解码结果按设备节奏输出。两端都要处理权限、设备变化和实时线程边界。它不负责拥塞控制，也不等于轨道在信令上的 `direction`。

## 先记住这三句

1. 采集把麦/摄像头/屏幕变成带格式与时间的帧；渲染按设备节奏把解码结果吐出去。
2. 约束请求 ≠ 实际 settings；`enabled` / `muted` / `ended` / 业务静音含义不同。
3. 实时回调里别干重活；预览链路与发送链路的旋转/格式要对齐或显式分叉。

## 问题边界

- **上游：** 设备权限、约束（分辨率/帧率/采样率）、系统音频/相机会话模式。  
- **下游：** 带元数据的 PCM/像素进入预处理与编码；解码帧进入同步与显示/扬声器。  
- **易混淆：**
  - 本地预览正常 ≠ 远端能收到（发送/协商另一条链）。  
  - `track.enabled=false` / `muted` / `ended` / 业务静音含义不同。  
  - 渲染“画得快”≠ 同步正确（见 [[音视频同步]]）。

## 核心机制

- 枚举 + 约束 → 实际 settings（以设置为准，不假设约束 100% 满足）。  
- 音频多按周期推/拉样本；视频按帧产生，分辨率/方向可动态变。  
- 渲染按播放时钟调度；欠载、阻塞、错误转换直接伤体验。

## 采集生命周期

```text
Enumerate/Permission -> ConstrainedOpen -> Running
Running -> DeviceSwitch/Interrupted -> Running
Running -> Stopped/Ended -> Released
```

1. 枚举与权限；授权前后列表可能不同。  
2. 请求约束。  
3. 读取**最终** settings。  
4. 每块数据带格式、时间、旋转/色彩等元数据进入处理链。  
5. 热插拔、撤权、来电、停轨要有明确迁移与释放。  

Native 还要区分：停发送、停 source、销毁设备——产品状态必须映射到真实媒体状态。更多路由细节见 [[音频路由与设备热插拔]]。

## 音频采集与播放

![[assets/images/client-hardware/usb-microphone-evan-amos.jpg|520]]

> [!example] USB 麦克风只是采集设备的一种外形
> 图中设备把麦克风、模数转换和 USB 接口集成在一起；操作系统最终仍向应用暴露设备、采样率、声道和回调块等契约。手机内置麦克风、阵列麦克风、蓝牙耳机和专业声卡的物理结构不同，不能由这张照片推断统一的延迟或采样能力。
>
> 图片来源：[Wikimedia Commons：USB-Microphone.jpg](https://commons.wikimedia.org/wiki/File:USB-Microphone.jpg)，Evan-Amos，Public domain。

- 明确：采样率、声道、样本格式、交错/平面、每回调帧数。  
- **采集时间**用于延迟与同步；用回调排队时刻冒充硬件时间会系统性偏。  
- AEC 需要与麦输入对齐的远端播放参考；参考点错误→回声或近端被挖空（[[回声消除]] / [[RTC 音频预处理状态机]]）。  
- 播放必须持续供数；在回调里打日志/抢锁/做重采样重活 → underrun，网络再好也断续。

## 视频采集与渲染

![[assets/images/client-hardware/webcam-logitech-c922.jpg|520]]

> [!example] 外置摄像头帮助区分硬件与视频帧
> 镜头、图像传感器和设备控制产生原始或半处理的视频帧；USB 只是它与主机连接的一种方式。应用拿到的不是“这台摄像头本身”，而是带像素格式、宽高、stride、时间戳和旋转等描述的帧。内置摄像头、采集卡和屏幕共享源会使用不同接口与缓冲类型。
>
> 图片来源：[Wikimedia Commons：Webcam (Logitech c922).jpg](https://commons.wikimedia.org/wiki/File:Webcam_(Logitech_c922).jpg)，Zsinytwiki，CC0。

- buffer 不只宽高：像素格式、plane、stride、色彩范围/矩阵、旋转。  
- 摄像头可降帧/改曝光；屏幕共享低帧率但文字锐利——编码策略不同。  
- 零拷贝纹理/硬件 buffer 有线程与寿命约束；用已释放纹理 → 绿屏/花屏/偶崩。  
- 渲染按计划呈现时间等待或丢帧，避免“解完立刻画”打乱同步。

## 具体例子

手机旋转后相机仍输出横向 buffer，但 `rotation` 元数据变了。若预处理已物理旋转像素，渲染再按元数据转一次，远端方向错误。约定只在一处旋转，并在编码与渲染边界断言“像素朝向”。

## 格式协商与转换

设备格式、编码器输入、渲染器格式常不一致。转换应落在**明确边界**，并计量成本。

| 边界 | 例子 | 注意 |
| --- | --- | --- |
| Camera → Encoder | NV12 → I420 | stride、plane、色度 |
| Mic → APM | 48 kHz 双声道 → 处理块 | 时间线连续 |
| Decoder → Display | 硬件帧 → Surface | 寿命与线程 |

避免每个模块各自猜格式、重复转换。分辨率/设备切换时**原子更新**描述与 buffer 池。

## 线程与所有权

- 采集回调、编码、渲染、UI 通常不同线程；跨线程只传明确所有权的帧。  
- 实时回调：无磁盘、无网络、无无界分配、无等 UI 锁。  
- 代次号：设备切换后旧回调必须丢弃。  
- 与 [[Native WebRTC 线程模型]] 对齐：别在网络线程做颜色转换。

## 工程要点

- 权限撤销与热插拔要可测、可恢复。  
- 旋转约定二选一贯穿全链路：“像素已旋”或“元数据描述旋转”。  
- 预览路径与发送路径的格式/旋转必须一致或显式分叉并测试。  
- 统计：实际格式、回调间隔、转换耗时、编码队列、渲染丢帧、underrun、设备事件。

## 常见误区与故障表现

| 现象 | 重点检查 |
| --- | --- |
| 本地预览好、远端黑 | 编码输入、发送状态、direction |
| 旋转/颜色错 | rotation、stride、色域、plane |
| 周期性爆音 | underrun、块长、重采样、回调阻塞 |
| 换设备后无声 | 新设备启动、旧回调代次、source 绑定 |
| 回前台很拖 | 恢复、积压队列、旧时间戳、关键帧 |

误区：以为约束请求等于实际格式；在音频回调里做 JSON 日志；预览旋正了发送链路又旋一次。

## 观测与验证

分开打点：采集时间 → 入编码 → 解码完成 → 实际呈现。  

用例：权限拒绝、拔插耳机/蓝牙、旋转、前后台、来电抢占、屏幕共享起停、低光降帧。  

听感/观感与指标一起看，不要只看“有没有帧”。
