# MCU

> [!tip] 阅读提示
> **前置：** [[WebRTC 拓扑选择]]、[[SFU]]、[[媒体服务器]]。
> **初读：** 先读“一句话说明”“问题边界”“处理流水线”和“场景示例”，弄清 MCU 用算力换什么。
> **深入：** 混音/合成截止、容量与故障隔离在选型或排障时再读。

## 一句话说明

MCU（Multipoint Control Unit）在服务端**解码**多路媒体，完成混音或画面合成，再**编码**成单路或少量输出。它用统一布局和下行简单，换取服务端计算量、额外延迟，以及“必须看见明文媒体”的能力边界。它不是 SFU 的别名。

## 问题边界

- **上游：** 多路已编码 RTP、各路时间戳/时钟、布局与混音策略、输出规格。
- **下游：** 新的编码时间线与码率、固定或少量视角的合成流、录制/网关用的统一格式。
- **不负责：** 替代业务信令；在 E2EE 不可见内容时做智能裁剪；把某路“透传原画”同时假装零转码成本。
- **易混淆：**
  - MCU 输出是**新媒体源**，不是原发送者码流的副本。
  - “终端只收一路”不等于总带宽更省——服务端入站与内部处理仍很重。
  - 音频 MCU + 视频 SFU 的混合拓扑很常见，不要一刀切。

## 核心机制

1. 接收并整理多路输入（解密、乱序、抖动、解码）。
2. 统一采样率/像素格式/时间基。
3. 音频混音、视频布局合成。
4. 按统一输出时钟产帧。
5. 再编码、封装、加密发送。

每一阶段都有截止时间：某路迟到时用上一帧、占位、PLC 或跳过，**不能让整路合成空等**。

```text
N 路 RTP
  -> decode / resample / scale
  -> mix (audio) / compose (video)
  -> encode (new timeline)
  -> 1..K 路出站
```

## 处理流水线

| 阶段 | 做什么 | 若卡住 |
| --- | --- | --- |
| 接收/解密 | 入站合法性、基本统计 | 单路失败应隔离 |
| 解码 | 像素/PCM | 缺参考→请求关键帧或占位 |
| 格式统一 | 采样率、色域、尺寸、旋转 | 错误转换→爆音/偏色 |
| 合成 | 布局、叠加、混音 | 必须有界队列 |
| 编码发送 | 新时间线、目标码率 | 拖慢则降规格/丢非关键 |

## 音频混合

- 不同采样率/声道/增益/设备时钟：先重采样与对齐。
- 简单相加易削波：要有增益预算、限幅或动态处理。
- **mix-minus**（每人听到的是“总混音减自己”）避免明显自声，但输出组合数上升。
- 大房间可只混活跃发言人，需平滑切换，避免听感突变。
- 舒适噪声/静音策略要定义，避免“全员 mute 后绝对死寂”或噪声门泵动。

## 视频合成

- 输入映射到统一合成时间轴；迟到可复用上一帧或占位。
- 裁剪缩放保持宽高比、像素格式、色彩范围、旋转。
- 固定布局 = 一个编码视角；接收端**不能**再像 SFU 那样自由选某人原画高清。
- 布局切换改变复杂度，可能抬升瞬时码率与编码延迟。
- 字幕/课件/水印叠加要计入像素率与时间线。

## 时间线与主时钟

MCU 内部时钟决定何时产出下一块混音和下一帧合成画面。

- 输入 RTP 时间戳用于**对齐内容**，不能直接当输出 RTP 时间戳。
- 输出是新源：连续的新序号/时间戳/SR 映射。
- 音画若共用一个合成时钟，漂移补偿策略要显式；详见 [[端到端延迟]]、[[音视频同步]]。

## 生命周期状态机

```text
Session: Created -> Mixing -> ReconfigLayout -> Mixing -> Stopping -> Closed
InputPin: Attaching -> Running -> Stall/Placeholder -> Running -> Detached
Output:  Starting -> Encoding -> BitrateAdapt -> Encoding -> Stopped
```

- 某一路 Detached 不应拖垮 Mixing。
- ReconfigLayout 期间定义：冻结末帧、淡入淡出、还是短暂降帧。
- 与录制共享合成器时，录制故障域要隔离，避免磁盘抖停实时出站。

## 与 SFU 对照

| 维度 | MCU | SFU |
| --- | --- | --- |
| 服务端是否解码 | 通常要 | 通常不要 |
| 终端下行 | 常 1 路合成 | 多路自选 |
| 个性化拥塞 | 弱（共享合成） | 强（每订阅独立） |
| E2EE 明文需求 | 高 | 可做纯转发 |
| 典型延迟代价 | 解码+合成+重编码 | 转发/选层 |

混合：课堂互动用 SFU，录制/大屏用 MCU 拉一路合成——见下方例子。

## 容量估算

至少拆开：

- 输入解码像素率 / 音频混合路数  
- 缩放合成像素率  
- 输出编码规格与会话数  
- 内存带宽、硬件编码器会话上限与 profile  

**粗例：** 9 路 720p30 解码再合成 1080p30 一路输出。瓶颈可能是 9 路解码像素吞吐，而不是单路 1080p 编码。硬件“最大 8 路编码会话”也可能先触顶。

## 工程要点

- 单路异常不得阻塞整条混合流水线。
- 测量混合队列与再编码给 E2E 增加的时间（P50/P95/P99）。
- 过载策略：降输出分辨率/帧率、减少混合人数、暂停非关键布局，而不是无限排队。
- 权限与内容安全：能解码就意味着能录制/分析——产品与合规要显式承认。

## 常见误区与故障表现

- **全员爆音：** 混音增益、削波、格式转换、时间块缺失。  
- **一路卡顿拖死所有人：** 流水线在等该输入，缺截止/占位。  
- **合成延迟爬升：** 解码/布局/编码队列无界，输出时钟被积压拖走。  
- **音画渐漂：** 输入映射、重采样补偿、输出主时钟。  
- **以为 MCU 一定更省终端带宽就选型：** 忽略服务端成本与延迟 SLA。

## 观测与验证

分段打点：接收 → 解码 → 合成 → 编码 → 发送；报告 P50/P95/P99，不要只报均值。

验收：单路断流占位、布局切换、全员 mute、突发大关键帧、CPU 限流降规格、录制磁盘慢是否污染实时出站。

## 具体例子

课堂：学员互动走 [[SFU]] 个性化订阅；录制与教室大屏由 MCU 生成“老师 + 课件 + 字幕”固定流。实时路径保持低延迟；MCU 路径单独设延迟与故障预算。MCU 磁盘写满时只丢录制，不影响 SFU 转发。
