# 媒体服务器

## 一句话说明

媒体服务器位于实时媒体路径中，按产品需要承担转发、混流、转码、录制、网关或媒体质量控制，不应与只负责业务消息的信令服务器混淆。

## 核心机制

- 接收并识别参与者、媒体流和轨道，维护发布、订阅及反馈路由。
- SFU 主要转发编码媒体；MCU 解码、合成后再编码；实际系统可以混合使用。
- 控制面决定谁可以发布或订阅，媒体面按既定路由高速处理包和反馈。

## 组成与边界

一个可运行的媒体服务通常包含以下职责，但它们不一定部署在同一进程：

- 接入与传输：ICE/DTLS/SRTP、拥塞反馈、连接保活和传输状态。
- 媒体路由：把业务发布/订阅映射到入站流与各订阅者的出站流。
- 包处理：识别 SSRC、MID、RID 与负载类型，必要时改写序列号、时间戳和扩展。
- 恢复与缓存：保存短期 RTP 包，处理 NACK/RTX、关键帧请求与层切换。
- 媒体处理：按产品需要执行解码、混音、转码、录制或网关互通。
- 控制与调度：鉴权、配额、房间状态、节点选择和故障迁移。

信令服务器可以告诉媒体服务器“用户 A 允许发布摄像头”，但只有媒体服务器知道这条发布最终对应哪个传输、SSRC 和编码层。两者必须共享稳定的业务标识与生命周期规则。

## 一条媒体包的路径

1. 入站传输完成解密和基本合法性检查。
2. 通过传输、MID/RID、SSRC 和轨道映射找到发布对象。
3. 更新接收统计、乱序状态与重传缓存，处理相关 RTCP 反馈。
4. 查询当前订阅者及其选层、静音、权限和带宽状态。
5. 为每个出站上下文维护连续的协议状态，重写并加密后发送。
6. 将排队、丢弃、层切换和反馈结果写入可观测系统。

任何一步都可能丢弃报文，因此“服务端收到了包”不能直接证明订阅端会收到或解码它。

## 状态模型

- 房间和参与者属于业务生命周期；传输、发布和订阅属于媒体生命周期。
- 一次重连可能保持业务参与者不变，却创建全新的 ICE/DTLS 传输和出站 RTP 状态。
- 轨道替换可能保留业务槽位，但 SSRC、编码器参数和时间线发生变化。
- 节点迁移需要定义旧状态何时失效、订阅怎样恢复以及是否请求关键帧。

## 工程要点

- 容量要同时核算带宽、包速率、CPU、内存、队列与加密开销。
- 每条转发链路应独立观测丢包、RTT、发送队列和所选编码层。
- 录制、转码和网关不是所有媒体服务器的默认职责。

## 容量与隔离

- 带宽容量要计入 IP/UDP/SRTP 开销、重传、探测、级联和峰值关键帧，而非只加总编码目标码率。
- 包速率会在低码率小包音频、数据通道和大量订阅时先于带宽成为 CPU 瓶颈。
- 队列必须有上限和过载策略；无限缓存只会把丢包问题转换成更严重的排队延迟。
- 录制、转码等重任务宜与实时转发隔离资源和故障域，防止磁盘或编码器抖动阻塞媒体线程。

## 常见故障与观测

| 现象 | 优先检查 |
| --- | --- |
| 服务端有入站但订阅端无包 | 发布到订阅映射、权限、选层状态、出站队列 |
| 只有新入会用户黑屏 | 参数集缓存、关键帧请求、切层起点 |
| 某订阅者频繁卡顿 | 该订阅者的拥塞控制、队列、RTX 与选层原因 |
| 整个节点延迟上升 | 事件循环、包处理耗时、队列深度、CPU steal 和 GC |
| 跨区房间偶发断流 | 级联路由、链路容量、状态传播与故障切换 |

日志和指标应能沿 `room -> participant -> transport -> publication -> subscription -> outbound RTP` 逐级关联，同时控制高基数字段，避免把用户 ID 直接作为无限维度的监控标签。
