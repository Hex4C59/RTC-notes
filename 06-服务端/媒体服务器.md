# 媒体服务器

> [!tip] 阅读提示
> **前置：** [[数据面与控制面]]、[[WebRTC 拓扑选择]]。
> **初读：** 读到「初读到此为止」就停。弄清：媒体服务器走**媒体路径**；信令说「谁可以做什么」，媒体服务决定「包怎么走」。
> **深入：** 状态模型、容量隔离与故障表，部署/排障时再读。

## 一句话说明

媒体服务器位于实时**媒体路径**中，按产品需要承担转发、混流、转码、录制、网关或媒体质量控制。它与只搬运业务消息的**信令服务器**职责不同：信令决定“谁被允许做什么”，媒体服务器决定“包怎么走、何时丢、如何恢复”。

## 先记住这三句

1. 媒体服务器 ≠ 信令房间服务：前者转发/混流/录制，后者管权限与会话语义。
2. SFU / MCU 是媒体服务的**形态**，不是互斥品牌；一个集群可以混合。
3. 「服务端收到包」≠「订阅端能解码」——映射、选层、关键帧、出站队列任一步都可能断。

## 问题边界

- **上游：** 终端或级联节点的 ICE/DTLS/SRTP 连接、发布声明、订阅意图、配额与鉴权结果。
- **下游：** 各订阅者的出站媒体、录制文件、网关对端、级联邻居。
- **不负责：** 完整业务账户体系；替代 CDN 点播；在未授权下“顺手转码”。
- **易混淆：**
  - 有 WebSocket 房间服务 ≠ 已具备媒体服务器。
  - SFU/MCU 是媒体服务器的**形态**，不是互斥品牌名；一个集群可混合。
  - “服务端收到包”≠ 订阅端可解码。

## 核心机制

- 识别参与者、传输、发布、订阅与轨道，维护反馈路由。
- [[SFU]] 侧重转发选层；[[MCU]] 侧重解码合成再编码；录制/转码/SIP 网关是可选能力。
- 控制面授权与媒体面转发必须共享稳定业务 ID 与生命周期规则。

## 组成与边界

可运行的媒体服务通常包含下列职责（不必同进程）：

| 职责 | 内容 |
| --- | --- |
| 接入与传输 | ICE/DTLS/SRTP、拥塞反馈、保活 |
| 媒体路由 | 发布/订阅 → 入站流 × 出站流 |
| 包处理 | SSRC/MID/RID/PT，必要时改写序号与扩展 |
| 恢复与缓存 | NACK/RTX、关键帧、层切换 |
| 媒体处理 | 解码、混音、转码、录制、网关（可选） |
| 控制与调度 | 鉴权、配额、房间状态、选点、迁移 |

信令可以说“A 允许发布摄像头”；只有媒体服务器知道最终落到哪条 transport、哪个 SSRC、哪一层。

## 一条媒体包的路径

1. 入站解密与合法性检查。  
2. 用 transport + MID/RID/SSRC/轨道映射找到发布对象。  
3. 更新接收统计、乱序与重传缓存；处理相关 RTCP。  
4. 查订阅者：选层、静音、权限、带宽。  
5. 每出站上下文维护协议状态，重写（若需要）并加密发送。  
6. 排队/丢弃/切层/反馈写入观测。  

任一步都可能丢包，因此入站计数上升不能证明远端有画。

```text
signal: allow publish/subscribe
media:  packet -> map -> route -> egress -> subscriber
feedback: NACK/PLI/TWCC -> local|upstream|ignore
```

## 具体例子

用户 A 信令进房成功，但观众 B 无画。媒体日志显示 A 的 Publication 在线，B 的 Subscription 选中高层却 `WaitingKeyframe` 超时。根因是关键帧请求被限流吞掉，而不是“ICE 失败”。按表先查订阅态与关键帧，而不是先抓公网。

## 状态模型

至少四条生命周期，不要揉成一个布尔值：

| 对象 | 含义 | 重连时常见变化 |
| --- | --- | --- |
| Room / Participant | 业务身份 | 可保持 |
| Transport | ICE/DTLS 会话 | 常新建 |
| Publication | 发布槽位与参数 | 可能 replaceTrack |
| Subscription | 某人对某发布的接收 | 常重建 |

```text
Participant (business)
  \- Transport (ICE/DTLS)  --restart--> new Transport
  \- Publication           --replaceTrack--> new SSRC/timeline
       \- Subscriptions...
```

节点迁移要定义：旧状态何时失效、订阅如何恢复、是否强制关键帧。详见 [[会议媒体路由与订阅]]、[[级联与边缘节点]]。

## 与 SFU / MCU / 网关的关系

- **纯 SFU 集群：** 实时会议主力；内容可对服务端不可见（E2EE）时仍可转发。  
- **MCU 节点：** 录制、大屏、SIP 互通、固定布局。  
- **转码/网关：** 协议或编码转换；成本接近 MCU 量级。  
- **录制旁路：** 最好从 SFU 抽流或接 MCU 输出，并隔离磁盘故障域。

选型总表见 [[WebRTC 拓扑选择]]。

## 容量与隔离

- 带宽：计入 IP/UDP/SRTP、RTX、探测、级联、关键帧峰值，不只加总编码器目标码率。  
- 包速率：低码率小包音频 + 大量订阅时，可能先于带宽打满 CPU。  
- 队列：必须有上限与过载策略；无限缓存只是把丢包变成更大延迟。  
- 隔离：录制/转码与实时转发分资源与故障域，防止磁盘或编码器抖动阻塞媒体线程。  
- 多租户：按 room/租户做配额，避免吵闹邻居。

**粗例：** 同节点 500 路音频订阅，每路 50 packet/s，仅音频就 25k packet/s；再加视频分片与 RTX，事件循环与 SRTP 会先于“带宽还剩很多”报警。

## 工程要点

- 观测键建议能串：`room → participant → transport → publication → subscription → outbound RTP`。  
- 高基数监控勿把无限 userId 当标签维度；用可控 ID 或采样。  
- 每条转发链路独立看丢包、RTT、队列、选层原因。  
- 控制面超时与媒体面超时分开配；不要用同一个 HTTP 超时套住 ICE。  
- 安全：令牌绑定流/房间；管理面与媒体面网络分区。

## 常见误区与故障表现

| 现象 | 优先检查 |
| --- | --- |
| 有入站无出站 | 映射、权限、选层、出站队列 |
| 仅新用户黑屏 | 参数集、关键帧、切层起点 |
| 单人卡众人差不多 | 是否误共享拥塞/选层 |
| 整节点延迟升 | 事件循环、包处理、队列、steal/GC |
| 跨区偶发断流 | 级联路由、容量、状态传播、切换 |

误区：把信令“进房成功”当媒体就绪；把 MCU 录制慢归因为公网；用平均码率做容量规划忽略突发。

## 观测与验证

- 控制面：鉴权失败率、进房到首包、订阅变更延迟。  
- 媒体面：入/出站包率与码率、复制倍数、队列、NACK 命中、关键帧等待、转码实时系数。  
- 体验：首帧、切层、恢复、跨区故障切换。  

压测要含：大小房混合、订阅抖动、网络恢复、节点杀死、磁盘满——不要只测空房或稳态满载。
