# SFU RTP 改写与反馈翻译

SFU 为每个订阅者选择性转发媒体时，不能只复制 UDP 包。层切换、暂停、丢包和重新订阅会打断上游序号与时间线；若 SFU 对下游改写 SSRC、序列号或时间戳，就必须同时翻译 NACK、RTX、RTCP SR/RR 和统计关系。

## 为什么需要独立出站上下文

发布者只有一条入站时间线，但每个订阅者收到的包集合不同。A 可能收高层，B 只收低层；A 的下行丢包也不应改变 B 的序号空间。因此每个订阅至少维护独立的出站 SSRC、下一序号、时间戳偏移、传输序号、发送历史、重传缓存索引和 RTCP 状态。

## 三种转发策略

- 完全透传：保留上游 SSRC、序号和时间戳。实现简单，但切源/切层会暴露不连续，下游反馈需准确路由到原流。
- 连续改写：为下游建立稳定 SSRC 和连续序号/时间戳。接收端体验稳定，但 SFU 必须维护双向映射。
- 分段重启：切换时显式启用新 SSRC 或新接收代次。状态边界清晰，但会触发更多协商、映射和解码恢复工作。

策略没有统一最优值，必须与客户端容忍能力、Simulcast/SVC、E2EE 可见元数据和调试需求一起决定。

## 出站映射状态

```text
InboundKey  = (publisher, inbound_ssrc, inbound_ext_seq)
OutboundKey = (subscriber, outbound_ssrc, outbound_ext_seq)

映射项至少保存：
入站/出站序号、入站/出站时间戳、发送代次、编码层、是否关键参考、
原始包或可重建载荷引用、实际下游发送时间、传输序号和过期时间。
```

映射必须有界。缓存窗口至少覆盖计划支持的 NACK 往返，但超过播放价值后应淘汰；缓存过短导致 NACK 未命中，过长则增加内存和旧包误用风险。

## 序列号改写

若上游收到序号 100、101、102，而 SFU 对某订阅者丢弃 101，直接透传会让下游看到缺口并发送无意义 NACK。连续改写可以输出 500、501，对应上游 100、102。此时下游 NACK 501 必须反查到上游 102 或 SFU 缓存中的对应载荷。

16 位序号会回绕，因此映射内部使用扩展序号并按每个出站 SSRC 独立维护。不要仅保存一个固定 offset：层切换、主动丢包、RTX 和源重启会让关系变成分段映射。

## 时间戳改写与切层

切换到另一个 Simulcast 层时，新层 RTP 时间戳可能与旧层有相同媒体时钟但不同起点。SFU 应在可解码切换点计算新的时间戳偏移，使下游时间线单调且与帧间隔一致。

时间戳连续不表示参考依赖连续。切层前还要等待目标层关键帧或明确的可解码切换点。若只有时间戳对齐而参考帧缺失，下游会收到“协议连续但不可解码”的黑屏流。

## SSRC 与头扩展处理

- 出站 SSRC 必须与 SDP/信令和 RTCP 上下文一致，发生冲突时创建新代次并清理旧状态。
- MID/RID 的保留、删除或改写要符合下游协商；不能把上游 RID 原样用于下游未协商的扩展 ID。
- TWCC transport sequence 是每条下游传输的观测空间，通常应重新分配并保存实际发送时间，不能沿用发布者到 SFU 的编号。
- abs-send-time、audio-level、视频旋转和依赖描述等扩展要按语义决定透传或重写；未知扩展只能安全跳过，不能猜测。

## NACK 与 RTX 翻译

1. 下游 NACK 指向出站媒体序号。
2. SFU 在该订阅的映射表中找到原始媒体包和发送代次。
3. 若缓存仍有效，按下游 RTX 协商生成新的 RTX 包，OSN 写原出站媒体序号，并分配出站 RTX 序号。
4. 若未命中且上游恢复仍来得及，可把请求翻译为上游序号；否则丢弃请求或触发更高级恢复。
5. 每次决策记录本地命中、上游转发、过期、映射缺失或限流原因。

不能把下游 RTX 包直接复用发布者发来的 SRTP 密文。每条 DTLS-SRTP 链路有独立安全上下文，SFU 必须在合法终止点重新保护出站报文。

## PLI/FIR 聚合

多个订阅者同时缺参考帧时，直接把所有 PLI 转发给发布者会产生关键帧风暴。SFU 应按发布流设置最小间隔、合并相近请求，并区分“已有关键帧正在传输”“目标层没有刷新点”和“新订阅必须请求刷新”。限流不能让新订阅无限黑屏，因此要保留请求原因和等待状态。

## RTCP SR/RR 翻译

- 下游 Sender Report 中的 SSRC、包数、字节数和 RTP/NTP 映射应描述 SFU 实际发送给该订阅者的流，而不是机械复制上游累计值。
- 下游 RR 针对出站 SSRC 和序号空间；SFU 用它评估该下行，不应直接合并成发布者上行丢包率。
- RTT 必须按每条链路分别计算。发布者到 SFU 与 SFU 到订阅者是两个网络段，简单相加或转发 LSR/DLSR 会混淆语义。
- 若要形成端到端诊断，应在监控层关联两段指标，而不是破坏 RTCP 的单段会话含义。

## 状态生命周期

```text
Created -> WaitingForKeyframe -> Forwarding -> Switching/Paused -> Closing
```

发布重连、replaceTrack、RID 变化和订阅重建都应产生明确代次。旧 NACK、旧关键帧、旧发送任务或旧 SRTP 上下文到达时必须因代次不匹配而被拒绝，不能污染新出站流。

## 并发和性能

- 入站包载荷可使用只读引用在多个订阅间共享，但每个出站头部和安全保护必须独立。
- 房间路由、出站 Pacer 和反馈处理若在不同线程，映射项要么不可变，要么通过单所有者序列更新。
- 容量不仅看 bit/s，还要看 packet/s、扩展改写、SRTP、缓存引用和扇出次数。
- 慢订阅者的发送队列必须有界，不能反压发布者或其他订阅者；过期视频包应按依赖安全丢弃。

## 可观测与验收

- 对每个订阅记录当前入站/出站 SSRC、RID、序号段、时间戳偏移、切层原因和代次。
- 记录 NACK 映射命中、本地 RTX、上游请求、缓存过期、PLI 聚合和关键帧等待时间。
- 用丢中间包、序号回绕、切层、暂停恢复、发布者重连和下游网络切换测试映射连续性。
- 从抓包验证下游序号连续、时间戳合理、TWCC 独立、RTCP 统计属于正确链路，并确认解码帧连续。

## 常见误区

- “SFU 不解码，所以无需理解视频帧”：选层和安全丢包仍需要关键帧与依赖信息。
- “序号减去固定偏移即可翻译”：丢包、切层和重启会产生多段映射。
- “所有订阅者的反馈可以取最差值”：每条下行容量和恢复状态必须独立。
- “SRTP 密文可直接复制”：不同端点链路通常具有不同密钥与包索引状态。
