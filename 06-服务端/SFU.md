# SFU

> [!tip] 阅读提示
> **前置：** [[WebRTC 拓扑选择]]、[[会议媒体路由与订阅]]；有 [[RTP]] / [[Simulcast]] 基础更好。
> **初读：** 先读“一句话说明”“问题边界”“入站与出站上下文”和“容量示例”，画清订阅矩阵。
> **深入：** 反馈闭环、选层、生命周期与故障观测在实现或排障时再读；改写细节见 [[SFU RTP 改写与反馈翻译]]。

## 一句话说明

SFU（Selective Forwarding Unit）接收参与者的**已编码**媒体，并按订阅关系**选择性转发**，通常不解码再合成画面。它用终端侧的编解码复杂度和多路下行，换取服务端更低的处理延迟与更好的横向扩展。它不是 MCU，也不代替信令房间与权限系统。

## 问题边界

- **上游：** 发布端推来的 RTP/SRTP、发布声明（mid/rid/层）、业务订阅意图、各下行的网络反馈。
- **下游：** 每个订阅者独立的出站媒体与 RTCP、选层结果、重传/关键帧策略。
- **不负责：** 业务信令语义（踢人、角色）、完整 E2EE 明文处理（看不见内容时无法智能裁剪/转码）、替代终端 AEC。
- **易混淆：**
  - SFU ≠ 对所有人广播同一份码流；选择性是核心。
  - “不解码” ≠ 不需要理解关键帧/依赖；选层和安全丢包仍要帧信息。
  - 房间人数 ≠ 负载；负载由**订阅矩阵 × 选中层 × 重传**决定。

## 核心机制

1. 为每个发布者维护**入站上下文**（识别、统计、短缓存）。
2. 路由层根据订阅、布局、能力与带宽，决定转哪路、哪一层。
3. 为每个订阅者维护**出站上下文**（序号/SSRC 策略、反馈、pacing、重传映射）。
4. 对 NACK/PLI/TWCC 等反馈做本地处理、聚合或回传上游。
5. 订阅变更、重连、切层时推进明确代次，避免旧状态污染。

```text
Publisher RTP
  -> Ingress (SSRC/RID/keyframe/cache)
  -> Router (subscribe × layout × bandwidth)
  -> Egress per subscriber (rewrite?/rtx/pacing)
  -> Subscriber
Subscriber feedback
  -> local RTX / aggregate PLI / translate / ignore
```

## 入站与出站上下文

SFU 不是把收到的 UDP 包原样复制给所有人。

| 侧 | 关键状态 | 典型错误 |
| --- | --- | --- |
| 入站 | SSRC、MID/RID、层、关键帧、接收统计、短缓存 | 把业务用户 ID 当唯一流键，重连后串流 |
| 路由 | 订阅集、布局、权限、层选择原因 | 全员共享一个“最低公共层” |
| 出站 | 每订阅者的发送时间线、RTCP、NACK 映射、队列 | 多订阅者共用一个序号空间 |

同一入站载荷可被多个出站**只读复用**，但每个订阅者的协议状态必须独立。完全透传 SSRC/序号调试简单，切层/切源易露不连续；改写则必须同步 RTCP/RTX 映射，详见 [[SFU RTP 改写与反馈翻译]]。

## 反馈闭环

1. 订阅端上报 TWCC、RR、NACK、PLI/FIR 等。
2. SFU 判断：本地可满足（缓存命中 RTX） / 需翻译给上游 / 应忽略（已过期）。
3. 每条下行的估计带宽驱动**该出站**的 pacing 与选层，而不是房间全局一个码率。
4. 多订阅者的 PLI 要聚合限流，避免发布端关键帧风暴。
5. 慢订阅者的出站队列必须有界，不能反压发布者或其他人。

## Simulcast 与 SVC 选层

- **Simulcast：** 各编码常有独立 SSRC/RID；升层等可解码起点，做出站时间线连续。
- **SVC：** 理解可丢弃依赖，不能按包大小随机丢层。
- 切层要有**迟滞**和最短保持时间，避免在阈值附近闪烁。
- 活跃发言人、屏幕共享、缩略图的清晰度/帧率/恢复优先级不同，选层目标函数不要写死成一种。

| 场景 | 更看重 | 选层倾向 |
| --- | --- | --- |
| 发言人大画面 | 清晰度、关键帧及时 | 高层 + 更快刷新 |
| 宫格缩略图 | 包率/带宽 | 低层或低时间层 |
| 屏幕共享 | 文字可读 | 偏空间质量，帧率可较低 |

## 生命周期状态机

```text
Publisher: Announced -> IngressReady -> Active -> Restarting -> Ended
Subscriber: Requested -> WaitingKeyframe -> Forwarding -> Switching/Paused -> Unsubscribed
```

- 新订阅：先绑定目标编码，再等关键帧；从任意 P 帧开转容易黑屏。
- 发布者重连 / replaceTrack：新代次；拒绝旧包、旧 NACK、旧 SSRC 映射。
- 取消订阅：停转发、放缓存引用、清反馈，避免“看不见仍占带宽”。
- 静音要区分：业务静音、停发、关轨道、网络断流——恢复路径不同。

## 与 MCU / 直连的取舍

| 形态 | 服务端 | 终端 | 延迟/扩展 |
| --- | --- | --- | --- |
| Mesh | 轻 | 上行多路 | 人少尚可 |
| SFU | 转发/选层 | 编多路或收多路 | 会议主流 |
| MCU | 解码混合再编码 | 简单 | 服务端重、延迟与成本高 |

详见 [[WebRTC 拓扑选择]]、[[MCU]]。E2EE 会限制内容感知与转码，但不取消 SRTP 与权限控制。

## 容量与算力

不能只按房间人数估算。

```text
出站总带宽 ≈ Σ(每个订阅选中层码率 + RTX/FEC/padding + 协议开销)
包速率   ≈ Σ(各出站 packet/s)   // 可能先于带宽把单核打满
```

**例子：** 20 人，每人看 1 路大画面 + 4 路缩略图。若大画面 1.2 Mbit/s、缩略图各 150 kbit/s，仅视频媒体出站粗算：

`20 × (1.2 + 4 × 0.15) = 20 × 1.8 = 36 Mbit/s`

再加上音频、RTX、头部开销与信令。若缩略图改成 SVC 时间层可降，则矩阵一变，容量结论就变。

## 工程要点

- 观测键至少是 `(room, publisher_stream, subscriber)`，不要只打 userId。
- 改写 SSRC/序号/时间戳时，RTCP 与重传映射必须同代次更新。
- 出站 pacing 与丢弃策略按订阅者隔离；记录丢弃原因（过期、欠费带宽、不可解码依赖）。
- 安全：SRTP 每条链路独立；不要假设可复制密文扇出。
- 版本相关行为（RID、dependency descriptor、TWCC 扩展 ID）以对接客户端为准。

## 常见误区与故障表现

- **按人数扩容：** 忽略订阅矩阵与包速率。
- **全员共有拥塞状态：** 一人弱网拖垮整房码率。
- **切层只改 RID 不等关键帧：** 黑屏/花屏。
- **PLI 原样风暴转发：** 周期性全员卡顿。
- **取消订阅不清理：** 幽灵转发占带宽。
- **把 SFU 排队当公网 RTT：** 分段看 ingress RTT 与 egress RTT。

## 观测与验证

**指标（入站流 × 出站订阅）：** 码率、包率、丢弃原因、缓存命中、选层原因、关键帧等待、NACK 命中/上游转发、队列等待、RTT 分段。

**验收场景：**

1. 新订阅从黑屏到出画的关键帧时延  
2. 升/降层迟滞与是否闪烁  
3. 单人弱网是否污染他人选层  
4. 发布者重连后代次隔离  
5. 取消订阅后出站归零  

抓包与 Stats 应对齐同一 `subscriber` 维度，详见 [[SFU RTP 改写与反馈翻译]]、[[WebRTC Stats]]。

## 具体例子

订阅者 B 从低层升到高层。路由层决定升层 → 出站进入 Switching → 等待高层关键帧 → 映射切换到新 RID/SSRC 策略 → Forwarding。若在关键帧前强行转发高层 P 帧，B 侧解码器缺参考，表现为黑屏，而 SFU 出站码率看起来“已经升高”。
