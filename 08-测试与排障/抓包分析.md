# 抓包分析

> [!tip] 阅读提示
> **前置：** [[测试与排障地图]]；协议侧见 [[RTP]]、[[RTCP]]；建联侧见 [[ICE 与 TURN 诊断]]。
> **初读：** 读到「初读到此为止」就停。弄清：先定抓包点再谈过滤；STUN→DTLS→RTP 识别；序列缺口 ≠ 一定是网络丢包。
> **深入：** 丢包恢复时序、加密边界与误判表，对照 Stats/日志做结论时再读。

## 一句话说明

抓包分析用线上实际报文还原连接、时序、丢包、反馈与发送节奏，是验证端点日志与网络行为的重要证据；加密媒体负载通常不能直接解释内容，且抓包点位置决定你“看见”的事实集合。

## 先记住这三句

1. 抓包点位置决定你「看见」的事实——发送端抓到 ≠ 接收端必达。
2. 识别顺序：缩五元组 → STUN/TURN → DTLS → 按 SSRC/PT 分流 RTP/RTCP。
3. SRTP 通常只能看头与时序；没有合法密钥别声称看到了帧内容。

## 问题边界

- **上游：** 抓包接口与过滤、会话时间窗、五元组/候选地址、应用日志中的 SSRC/MID。
- **下游：** 可复核的时序结论（握手停滞、序列缺口、NACK/RTX 往返、pacing 突发）、与 Stats/服务日志的互证。
- **易混淆：**
  - 发送端抓到 ≠ 接收端必达。
  - 序列缺口 ≠ 一定是网络丢包（乱序、抓包丢、offload 聚合都会像缺口）。
  - 平均包间隔好看 ≠ 无微突发 / 无关键帧尖峰。
  - 能解 SRTP ≠ 可以随意导出明文（授权与脱敏仍是硬约束）。

## 核心机制

1. **先定抓包点与方向**，再谈过滤与解码。  
2. 用时间、接口、IP/端口与会话日志缩小流；再识别 STUN/TURN → DTLS → RTP/RTCP。  
3. 按 SSRC、Payload Type、MID/RID、方向分流后，算间隔、缺口、乱序与反馈时序。  
4. 把报文事件与 [[WebRTC Stats]]、应用日志对齐；单包不下最终结论。  
5. 对 SRTP 只信可见头与时序/包长，除非有合法密钥与受控解密环境。

## 先定义抓包点

同一通话在不同位置看到的事实不同：

| 位置 | 能证明 | 不能证明 |
| --- | --- | --- |
| 客户端网卡 | 本端发往 NAT/TURN/SFU 的加密流量与本端时序 | 对端真实接收、解码渲染 |
| TURN 节点 | 客户端↔中继、中继↔对端两段是否在跑 | 媒体内容、选层策略细节 |
| SFU 入站 | 媒体到达服务端 | 已进入某订阅出站 |
| SFU 出站 | 选层/改写/丢弃/pacing 后的实际发送 | 接收端播放体验 |
| 接收端网卡 | 最接近用户收到的网络包 | 解码成功与口型/卡顿感 |

跨点比较需要时钟同步和稳定流标识。NAT、TURN、SFU 会改写五元组、SSRC、序列号甚至 PT，必须靠服务端映射日志关联，不能只靠“看起来像同一路”。

## 协议识别顺序

```text
narrow 5-tuple / time window
  -> STUN/TURN txs (ICE / allocation)
  -> DTLS handshake vs ICE timeline
  -> RTP/RTCP by SSRC / PT / MID-RID
  -> gaps, reorder, RTCP feedback, recovery timing
```

1. 用时间、接口、IP/端口和会话日志缩小 UDP/TCP 流。  
2. 识别 STUN/TURN 事务：候选检查、allocation、permission/channel。  
3. 看 DTLS 相对 ICE 的时间：是否重传、卡在哪一 flight。  
4. 对 RTP/RTCP 按 SSRC、PT、MID/RID、方向分流。  
5. 计算包间隔、序列缺口、乱序、RTCP 反馈与恢复包时序。

Wireshark 常用显示过滤（解析能力依版本）：

```text
stun
dtls
rtp || rtcp
rtp.ssrc == 0x12345678
udp.port == 3478
```

动态端口未被自动识别为 RTP 时，可用 Decode As **辅助**，但必须先确认协议——不能把任意 UDP 强制解码后当成事实。

## 丢包与恢复分析

- 序列缺口后很快出现原序列或 RTX：说明发起了恢复；还要看是否赶在[[播放截止时间]]前到达。  
- NACK 前间隔 ≈ 检测 + 反馈延迟；NACK→重传到达 ≈ 反馈路径 + 发送侧处理。  
- PLI 后观察：编码端何时出关键帧、SFU 是否转发、接收端何时恢复解码。  
- FEC 恢复未必表现为同序列重传，需结合接收端恢复统计与负载语义。

**抓包自身也会丢。** 检查 capture dropped、主机负载、硬件 offload；发送端抓包里的大段聚合或校验和异常，可能来自 offload，而非线上真实报文形态。

## 加密边界

SRTP 通常仍暴露路由所需的部分 RTP 头，因此可分析 SSRC、序列、时间戳、包长与时序；媒体负载、部分头扩展及鉴权保护取决于配置。**没有合法会话密钥时，不应声称从负载看到了帧内容或编码错误。**

即便能解密，也要控制密钥与媒体内容的访问范围。诊断导出可能含语音、画面与地址，遵守授权、脱敏与保存期限。

## 工程要点

- 报告开头写清：接口、位置（NAT 前/后）、方向、过滤、时区、会话 ID。  
- 保存可复现的过滤表达式与少量标记包号，便于他人复核。  
- 与 Stats（packetsLost、nackCount、jitterBuffer、candidate-pair）互证，避免“包好看、体验差”或反过来。  
- 长通话分段抓：全量 pcap 巨大且易丢；异常窗口前后各留足够上下文。  
- SFU 场景优先成对抓入站+出站，否则选层/改写会被误判成“神秘丢包”。

## 常见误判

| 误判 | 更稳妥的做法 |
| --- | --- |
| 乱序当丢包 | 等合理重排序窗口，看后续是否补齐 |
| 本端发出即对端必达 | 对照接收端/中间节点抓包或 Stats |
| 重复包全归因 RTX | 区分网络复制、应用重发、抓包重复 |
| 未同步时钟比单向时延 | 只用相对间隔，或先做时钟对齐 |
| 只看平均间隔 | 看关键帧突发与 pacing 微突发分布 |
| Decode As 后当真理 | 先用 STUN/DTLS/头模式确认协议 |

## 观测与验证

- **最小证据包：** 抓包点说明 + 过滤式 + 异常时间窗 + 相关 SSRC 列表 + 对齐的 Stats/日志片段。  
- **注入场景：** 人工丢包、乱序、带宽阶跃、强制 relay、ICE restart、进出后台。  
- **自检：** capture drop 计数、是否开启 offload、是否抓到对称方向。  
- **结论句式：** “在 T0–T1，ssrc=… 出现 N 个序列缺口；NACK 后 RTX 中位时延 X ms；接收端 `packetsLost` 同期上升”——写清限制（未解密、单点抓包等）。
