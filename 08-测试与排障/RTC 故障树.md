# RTC 故障树

> [!tip] 阅读提示
> **前置：** [[测试与排障地图]]。
> **初读：** 读到「初读到此为止」就停。弄清：先固定五上下文，再沿会话→连接→传输→媒体→呈现缩小范围；每个「是」都要有证据。
> **深入：** 分段定位、假设验证与工单字段，实战复盘时再读。

## 一句话说明

先把用户现象转成可验证的阶段事实，再沿会话 → 连接 → 传输 → 媒体 → 呈现逐层缩小范围。每个判断都要有状态、指标、日志、报文或可重复实验支撑——重启碰巧修好不算根因闭合。

## 先记住这三句

1. 排障 = 现象 → **可验证阶段事实** → 逐层缩小；重启碰巧修好 ≠ 根因闭合。
2. 动手前固定五上下文：时间/时区、会话、方向、版本、环境——不要同时改多个变量。
3. ICE connected ≠ 媒体在流；每个「是」都要看到对应计数/状态证据。

## 问题边界

- **上游：** 现象描述、时间/时区、会话与方向、版本与环境。
- **下游：** 最小故障范围、可证伪假设、修复与回归结论。
- **易混淆：**
  - “房间没声音”可能只是 `B -> A` 单向。  
  - ICE connected ≠ 媒体在流。  
  - 丢包截图 ≠ 网络根因（未看抓包点/乱序/恢复）。  
  - 服务端平均值 ≠ 某订阅者单向问题。

## 使用方式

排障前固定五项上下文：

1. 发生时间与时区  
2. 会话 / 参与者标识  
3. 问题方向（谁→谁，音/视）  
4. 客户端与服务端版本  
5. 网络与设备环境  

然后再进决策树。不要同时改多个变量。

## 总体决策树

```text
业务是否进入通话？
├─ 否：鉴权、房间状态、信令消息
└─ 是：本地媒体是否正常产生？
   ├─ 否：权限、设备、Track、采集回调
   └─ 是：协商是否完成且方向正确？
      ├─ 否：Offer/Answer、SDP、Transceiver
      └─ 是：ICE 是否选中候选对？
         ├─ 否：候选、STUN/TURN、检查与提名
         └─ 是：DTLS/SRTP 是否建立？
            ├─ 否：指纹、角色、握手报文
            └─ 是：RTP 是否逐段增长？
               ├─ 否：发送、路由、选层、网络路径
               └─ 是：能否解码并实际呈现？
                  ├─ 否：负载类型、参数集、参考帧、设备
                  └─ 是：检查质量、延迟和同步闭环
```

每个“是”都要有证据。例如 ICE `connected` 只证明至少有候选对工作；确认媒体还要看到对应 RTP 的字节/包持续增长。

## 五个入口

1. 会话未建立 → [[WebRTC 状态机诊断]]  
2. 网络未连通 → [[ICE 与 TURN 诊断]]  
3. 有连接无媒体 → [[Stats 指标与故障映射]]  
4. 卡顿/花屏 → [[抓包分析]]  
5. 只在弱网复现 → [[网络仿真]]  

浏览器时间线辅助：[[webrtc-internals]]。

## 按现象选择第一组证据

| 用户现象 | 第一组证据 | 下一步区分 |
| --- | --- | --- |
| 无法加入房间 | 业务/信令日志 | 鉴权、消息未达、状态机拒绝 |
| 一直连接中 | ICE 状态、pair、TURN 日志 | 无候选、检查失败、提名失败 |
| 单向无声 | 两端 audio RTP 与采集/播放 | 未采集、未发送、未路由、未播放 |
| 有声黑屏 | video packets、framesDecoded、PLI | 未收包、缺关键帧、解码/渲染 |
| 马赛克/花屏 | 序列缺口、NACK/RTX、关键帧 | 恢复失败、参考链损坏 |
| 延迟越来越大 | pacing、发送队列、jitter buffer | 上行/网络排队、接收缓冲积累 |
| 偶发全员卡顿 | 服务端节点与跨区链路 | 共享资源、关键帧风暴、级联 |

## 分段定位方法

沿：采集 → 编码 → 发送 →（网络/SFU 入/出）→ 收包 → 解码 → 渲染，检查单调计数。相邻两段之间首次“不再增长”或异常丢弃处，通常就是最小故障范围。

示例：发送端 `framesEncoded`/`bytesSent` 涨，SFU 入涨但订阅出不涨 → 查服务端路由/选层；订阅端 `packetsReceived` 涨而 `framesDecoded` 不涨 → 转向编解码/参考帧，而不是继续改 ICE。

## 证据原则

- 单次快照只能提假设，不能证根因。  
- 先确认时间范围、方向、流标识、版本，再比多种证据。  
- 修复后回到同一条件，确认体验与协议指标同时改善。

## 时间线与代次

- 墙上时间跨系统对齐；单调时间算本进程耗时。  
- 重连、ICE restart、重协商、换轨分配新代次；旧事件不覆盖新状态。  
- 把 Offer/Answer、pair 选中、DTLS、首 RTP、首解码、首呈现放同一时间线。  
- 状态迁移不可漏采；包级日志要限流，避免诊断阻塞实时线程。

## 形成与验证假设

1. 提出可证伪假设（例：“B 的视频在 SFU 订阅路由后停止”）。  
2. 写明成立/不成立各应看到什么。  
3. 补采最小证据；不同时改多变量。  
4. 在基线、故障、恢复三阶段重复。  
5. 验证故障指标、体验与资源副作用。  

完整结论应含：影响范围、触发条件、故障阶段、直接证据、根因机制、修复与回归结果。

## 不可靠的排障方式

- 见丢包就归因网络，未确认抓包点、乱序、迟到与恢复。  
- 只比单次 Stats 快照，未对累计计数求差。  
- 重启“修好”后停止分析，泄漏/状态污染根因保留。  
- 生产直接注入网络规则，无隔离管理链路与回滚。  
- 用服务端整体均值解释某订阅者的单向问题。

## 观测与验证

- **最小工单字段：** 五上下文 + 决策树走到的节点 + 第一组证据链接。  
- **闭合标准：** 同条件复测通过，且相关 Stats/日志同向改善。  
- **升级信号：** 全员/跨区/仅某节点 → 尽早拉服务端与级联视角。

## 多端协作时的分工

| 角色 | 先取什么 |
| --- | --- |
| 客户端 | 状态时间线、Stats 窗口、internals 导出 |
| 网络/TURN | allocation、permission、抓包点 |
| SFU | 入站/出站计数、选层、订阅映射 |
| 质量 | 仿真复现脚本与基线对比 |

结论合并时以**同一时间窗与同一流 ID**为键，不要各说各的“大概那会儿”。
