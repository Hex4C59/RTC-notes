# RTC 故障树

## 使用方式

先把用户现象转换成可验证的阶段事实，再沿会话、连接、传输、媒体和呈现逐层缩小范围。每个判断都要有状态、指标、日志、报文或可重复实验支撑。

排障前先固定五项上下文：发生时间与时区、会话/参与者标识、问题方向、客户端和服务端版本、网络与设备环境。“A 听不到 B”只说明 `B -> A` 方向异常，不能直接说整个房间没声音。

## 总体决策树

```text
业务是否进入通话？
├─ 否：鉴权、房间状态、信令消息
└─ 是：本地媒体是否正常产生？
   ├─ 否：权限、设备、Track 状态、采集回调
   └─ 是：协商是否完成且方向正确？
      ├─ 否：Offer/Answer、SDP、Transceiver
      └─ 是：ICE 是否选中候选对？
         ├─ 否：候选、STUN/TURN、检查与提名
         └─ 是：DTLS/SRTP 是否建立？
            ├─ 否：指纹、角色、握手报文
            └─ 是：RTP 是否逐段增长？
               ├─ 否：发送、路由、选层、网络路径
               └─ 是：能否解码并实际呈现？
                  ├─ 否：负载类型、参数集、参考帧、设备
                  └─ 是：检查质量、延迟和同步闭环
```

每个“是”都要由证据支持。例如 ICE `connected` 只证明至少有候选对工作；确认媒体还要看到相应 RTP 流的字节和包计数持续增长。

## 五个入口

1. 会话未建立：从 [[WebRTC 状态机诊断]]检查业务状态与协商状态。
2. 网络未连通：从 [[ICE 与 TURN 诊断]]检查候选、连通性检查和中继。
3. 有连接无媒体：用 [[Stats 指标与故障映射]]区分未发送、未接收、未解码和未渲染。
4. 媒体卡顿或花屏：用 [[抓包分析]]验证丢包、反馈、关键帧和码率变化。
5. 只在弱网复现：用 [[网络仿真]]建立基线、注入、恢复和对照实验。

## 按现象选择第一组证据

| 用户现象 | 第一组证据 | 下一步区分 |
| --- | --- | --- |
| 无法加入房间 | 业务/信令日志 | 鉴权失败、消息未达、状态机拒绝 |
| 一直连接中 | ICE 状态、candidate pair、TURN 日志 | 无候选、检查失败、提名失败 |
| 单向无声 | 两端 audio RTP 与采集/播放指标 | 未采集、未发送、未路由、未播放 |
| 有声音黑屏 | video packets、framesDecoded、PLI | 未收包、缺关键帧、解码或渲染失败 |
| 马赛克/花屏 | 序列缺口、NACK/RTX、关键帧 | 丢包恢复失败、参考链损坏 |
| 延迟越来越大 | pacing、发送队列、jitter buffer | 上行排队、网络排队、接收缓冲积累 |
| 偶发全员卡顿 | 服务端节点与跨区链路 | 共享资源、关键帧风暴、级联故障 |

## 分段定位方法

沿发送端采集、编码、发送，网络/SFU 入站与出站，接收端收包、解码、渲染逐段检查单调计数。相邻两段之间首次出现“不再增长”或异常丢弃的位置，通常就是最小故障范围。

例如发送端 `framesEncoded` 与 `bytesSent` 增长，SFU 入站增长但对应订阅出站不增长，应检查服务端路由/选层；若订阅端 `packetsReceived` 增长而 `framesDecoded` 不增长，应转向编解码与参考帧，而非继续修改 ICE。

## 证据原则

- 单一截图或一次快照只能提出假设，不能证明根因。
- 先确认时间范围、方向、流标识和软件版本，再比较多种证据。
- 修复后回到同一测试条件，确认用户体验和协议指标同时改善。

## 时间线与代次

- 所有组件记录可跨系统对齐的墙上时间，同时用单调时间计算本进程耗时。
- 重连、ICE restart、重新协商和轨道替换要分配新代次，旧事件不能覆盖新状态。
- 将 Offer/Answer、候选对选中、DTLS 完成、首个 RTP、首个解码帧和首次呈现放在同一时间线。
- 日志采样不能遗漏状态迁移；高频包级日志则要限流，防止诊断本身阻塞实时线程。

## 形成与验证假设

1. 用现象和第一组证据提出一个可证伪假设，例如“B 的视频在 SFU 订阅路由后停止”。
2. 说明若假设成立应该观察到什么，若不成立又会看到什么。
3. 补采最小必要证据，不同时修改多个变量。
4. 在稳定基线、故障条件和恢复阶段重复实验。
5. 修复后验证故障指标、用户体验及资源副作用。

一条完整结论应包含：影响范围、触发条件、故障阶段、直接证据、根因机制、修复和回归结果。

## 不可靠的排障方式

- 看到丢包就立刻归因网络，未确认抓包点、乱序、迟到和恢复结果。
- 只比较单次 Stats 快照，未对累计计数求差。
- 通过重启“修好”后停止分析，导致资源泄漏、状态污染等根因保留。
- 在生产环境直接注入网络规则，却没有隔离管理链路和回滚步骤。
- 用服务端整体平均值解释某个订阅者的单向问题。
