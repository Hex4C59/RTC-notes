# 网络仿真

> [!tip] 阅读提示
> **前置：** [[测试与排障地图]]；观测见 [[Stats 指标与故障映射]]；机制见 [[GCC]]、[[丢包恢复策略]]。
> **初读：** 读到「初读到此为止」就停。弄清：在隔离环境注入已知损伤，验证策略是否可重复——不替代线上未知拓扑的根因取证。
> **深入：** netem 命令、分阶段指标与常见实验错误，搭弱网台架时再读。

## 一句话说明

在受控环境注入带宽限制、时延、抖动、随机/突发丢包、乱序和重复，验证 RTC 的恢复、自适应和回落是否**可重复**。它回答“策略在已知损伤下怎么动”，不替代线上未知拓扑的根因取证。

## 先记住这三句

1. 仿真回答「策略在参数 P 下怎么动」；证明媒体**真的经过**损伤点，再信结果。
2. 「5% 丢包」必须说清随机 vs 突发；上行/下行要分开测。
3. 验收不只「未断线」：还看延迟回落、队列排空、恢复是否振荡——四阶段：基线→注入→稳定→恢复。

## 问题边界

- **上游：** 隔离拓扑与接口、损伤参数、媒体样本与版本锁定。
- **下游：** 基线→注入→稳定弱网→恢复四阶段的指标与体验结论。
- **易混淆：**
  - “5% 丢包”未说明随机 vs 突发 → 不可比。  
  - 通话未断 ≠ 验收通过（还看延迟回落、队列排空、是否振荡）。  
  - 规则加在错误接口/方向 → 媒体根本没经过 qdisc。  
  - 测试机 CPU 打满 → 编码掉帧被误当成网络损伤。

## 核心机制

1. 实验四阶段：稳定基线 → 故障注入 → 持续观察 → 网络恢复。  
2. 上行、下行、双向分别测；同平均丢包率下随机与突发结果不同。  
3. 对照固定：媒体样本、版本、配置、方向、统计窗口、重复次数。  
4. 用抓包或计数器**验证规则方向**，再信结果。

**图在说什么：** 固定源与双侧抓包夹住损伤点，用控制器统一施加/撤销 netem 等参数，才能对比 Stats 与 QoE。

```mermaid
flowchart LR
    S["发送端: 固定媒体源 + Stats"] --> ST["发送侧抓包点"]
    ST --> E["隔离损伤点: netem / TBF / 路由器"]
    E --> RT["接收侧抓包点"]
    RT --> R["接收端: 解码、播放、Stats、QoE"]
    C["实验控制器"] -->|应用 / 撤销明确参数| E
    C -->|统一时间窗与测试编号| S
    C -->|统一时间窗与测试编号| R
    E -->|qdisc 计数和配置快照| C
```

最关键的不是 `netem` 命令本身，而是证明媒体确实经过这个隔离损伤点，并能把两端 Stats、两侧抓包、规则计数和用户体验对齐到同一个实验时间窗。若损伤接口同时承载 SSH 或管理流量，台架边界就不合格。

## 损伤模型

| 参数 | 代表什么 | RTC 中常见影响 |
| --- | --- | --- |
| 带宽上限 | 路径可持续吞吐 | 发送队列、降码率、选层 |
| 固定时延 | 传播/处理基线 | RTT、交互性、重传价值 |
| 抖动 | 到达时间变化 | jitter buffer、迟到丢弃 |
| 随机丢包 | 独立概率损失 | NACK/RTX、PLC/FEC |
| 突发丢包 | 连续相关损失 | 参考帧损坏、长段音频隐藏 |
| 乱序/重复 | 重排或复制 | 接收窗口、去重、误报丢包 |
| 队列长度 | 瓶颈缓存容量 | 丢包 vs bufferbloat |

只写“5% 丢包”不够：独立随机 5% 与周期性连续丢 500 ms，破坏与恢复路径完全不同。

## 实验设计

1. 无损基线足够长，确认无掉帧与资源瓶颈。  
2. 只改一个主要变量；记录规则作用的接口、方向与时间。  
3. 进入稳定损伤阶段，观察估计、降级、恢复与体验。  
4. 撤销损伤，继续看码率、队列、缓冲、画质能否恢复。  
5. 重复多次，报告分布与失败率，不挑一次成功。

上行与下行要分开验证方向：发送端 egress 常模拟该端上行；接收方向可能需对端、路由器、IFB 或独立 netns。

## Linux netem 示例

仅用于隔离测试接口 `veth-rtc`；确认管理/SSH 不经过它：

```bash
# 80 ms 基础延迟、20 ms 波动、相关随机丢包和 2 Mbit/s 限速
sudo tc qdisc add dev veth-rtc root netem \
  delay 80ms 20ms distribution normal \
  loss random 2% 25% \
  rate 2mbit

tc -s qdisc show dev veth-rtc

sudo tc qdisc del dev veth-rtc root
```

`netem rate` 适合基础实验；更精确瓶颈队列可组合 HTB/TBF 与 netem。参数以当前内核与 `tc-netem(8)` 为准。

## 分阶段指标

| 阶段 | 看什么 |
| --- | --- |
| 基线 | 编解码帧率、端到端延迟、CPU、设备稳定 |
| 注入瞬间 | 发送队列、RTT、丢包、NACK/RTX/FEC、BWE 反应时延 |
| 稳定弱网 | 目标/实际码率、所选层、音频隐藏、视频卡顿 |
| 恢复 | 升码速度、队列排空、关键帧成本、是否振荡 |

## 推荐测试场景

- 带宽 5 Mbit/s → 800 kbit/s 阶跃，30 s 后恢复  
- RTT 40 ms → 300 ms，观察重传是否仍有价值  
- 2% 随机丢包 vs 500 ms 周期性突发对照  
- 上行拥塞 vs 下行拥塞分测  
- Wi-Fi↔蜂窝 + ICE restart 与媒体连续性  
- 弱网恢复时多订阅同时要关键帧，观察突发与服务端限速  

## 工程要点

- 不在承担 SSH/管理流量的接口上直接施破坏性规则；用 netns/容器/专用链路。  
- 同步采集：原始配置、命令、结构化日志、Stats、抓包、体验指标。  
- 验收不只“未断线”：延迟能否回落、队列是否排空、恢复流量是否受控。  
- 实验结束确认规则已移除，避免污染后续基线。

## 常见实验错误

| 错误 | 后果 |
| --- | --- |
| 规则在错误接口/方向 | 媒体未经过损伤 |
| 限速未控队列长度 | 测到超长 bufferbloat |
| 测试机 CPU 已满 | 编码掉帧误当网络 |
| 实时摄像头内容不固定 | 码率/质量不可比 |
| 结束未删 qdisc | 污染后续基线 |
| 一次成功当结论 | 无分布、无失败率 |

## 结果报告

记录拓扑、接口、完整命令、起止时间、媒体样本、版本、重复次数、原始证据路径。结论同时写体验与机制，例如：

> 带宽下降后 1.8 s 内降至目标层，发送队列 P95 ≤ 120 ms；恢复后 6 s 升层且无关键帧风暴。

而不是只写“弱网表现良好”。

## 观测与验证

- **方向自检：** 注入后抓包/计数是否只在预期方向变化。  
- **对照：** 同脚本无损 vs 损伤各 N 次。  
- **互证：** Stats 窗口与[[抓包分析]]、服务端选层日志对齐。


## 与线上事故的关系

仿真证明“在参数 P 下策略行为符合预期”；线上事故还需要证明“用户路径当时近似 P”。两者用同一套指标窗口对齐：

1. 线上 Stats 估出大致 RTT/丢包/带宽形态  
2. 在台架复现接近形态  
3. 对比降级与恢复曲线是否同族  
4. 再改策略或配置，用仿真回归  

不要用仿真成功直接宣布线上已修好，除非线上同窗指标也改善。
