# 网络仿真

## 一句话说明

网络仿真在受控环境中注入带宽限制、时延、抖动、随机或突发丢包、乱序和重复，用来验证 RTC 的恢复、自适应和回落过程是否可重复。

## 核心机制

- 实验由稳定基线、故障注入、持续观察和网络恢复四个阶段组成。
- 上行、下行与双向损伤要分别测试；相同平均丢包率下，随机和突发模型会产生不同媒体结果。
- 所有对照应固定媒体样本、版本、配置、方向、统计窗口和重复次数。

## 损伤模型

| 参数 | 代表什么 | RTC 中常见影响 |
| --- | --- | --- |
| 带宽上限 | 路径可持续吞吐 | 发送队列、降码率和选层 |
| 固定时延 | 传播/处理基线 | RTT、交互性和重传价值 |
| 抖动 | 包到达时间变化 | jitter buffer、迟到丢弃 |
| 随机丢包 | 独立概率损失 | NACK/RTX、PLC/FEC |
| 突发丢包 | 连续相关损失 | 参考帧损坏、长段音频隐藏 |
| 乱序/重复 | 路径重排或复制 | 接收窗口、去重和误报丢包 |
| 队列长度 | 瓶颈缓存容量 | 丢包与 bufferbloat 的取舍 |

只写“5% 丢包”不够。5% 独立随机丢包与每隔一段时间连续丢 500 ms，对音视频的破坏和恢复策略完全不同。

## 实验设计

1. 在无损网络运行足够长的基线，确认系统本身没有掉帧和资源瓶颈。
2. 只改变一个主要变量，记录规则真正作用的接口、方向与时间。
3. 等系统进入稳定损伤阶段，观察估计、降级、恢复和用户体验。
4. 撤销损伤，继续观察码率、队列、缓冲和画质能否恢复。
5. 重复多次，报告分布和失败率，不只挑一次成功结果。

上行与下行要分开：在发送端 egress 加规则通常模拟该端上行；接收方向可能需要在对端、路由器、IFB 或独立网络命名空间处理。实际方向必须用抓包或计数器验证。

## Linux netem 示例

以下示例只适用于隔离的测试接口 `veth-rtc`，执行前应确认管理和 SSH 流量不经过它：

```bash
# 80 ms 基础延迟、20 ms 波动、相关随机丢包和 2 Mbit/s 限速
sudo tc qdisc add dev veth-rtc root netem \
  delay 80ms 20ms distribution normal \
  loss random 2% 25% \
  rate 2mbit

# 查看实际规则与统计
tc -s qdisc show dev veth-rtc

# 实验完成后移除该接口上的 root qdisc
sudo tc qdisc del dev veth-rtc root
```

`netem rate` 适合基础实验；需要更精确的瓶颈队列模型时，可组合 HTB/TBF 与 netem。命令和参数支持应以当前内核与 `tc-netem(8)` 为准。

## 工程要点

- 不在承担 SSH 或管理流量的接口上直接施加破坏性规则，应使用隔离命名空间、容器或专用链路。
- 同步采集原始配置、命令、结构化日志、Stats、抓包和用户体验指标。
- 不用“通话未断”代替验收；还要检查延迟能否回落、队列是否排空和恢复流量是否受控。

## 分阶段指标

- 基线：编解码帧率、端到端延迟、CPU 和设备稳定性。
- 注入瞬间：发送队列、RTT、丢包、NACK/RTX/FEC 和带宽估计反应时间。
- 稳定弱网：目标码率、实际发送码率、所选层、音频隐藏和视频卡顿。
- 恢复阶段：探测和升码率速度、队列排空、关键帧成本、画质恢复和是否振荡。

## 推荐测试场景

- 带宽从 5 Mbit/s 阶跃降到 800 kbit/s，30 秒后恢复。
- RTT 从 40 ms 升到 300 ms，观察重传是否仍有价值。
- 2% 随机丢包与 500 ms 周期性突发丢包对照。
- 上行拥塞与下行拥塞分别测试，确认发送控制归属。
- Wi-Fi 到蜂窝切换，结合 ICE restart 与媒体连续性。
- 弱网恢复时多订阅同时请求关键帧，观察突发与服务端限速。

## 常见实验错误

- 规则加在错误接口或方向，实际媒体未经过该 qdisc。
- 限速后未控制队列长度，测到的是超长 bufferbloat 而非预期带宽上限。
- 测试机 CPU 已满，把编码掉帧误认为网络损伤。
- 使用摄像头实时内容导致每次画面复杂度不同，无法比较码率与质量。
- 实验结束未确认规则移除，污染后续基线。

## 结果报告

记录拓扑、接口、完整命令、开始/结束时间、媒体样本、版本、重复次数和原始证据路径。结论应同时说明体验结果与协议机制，例如“带宽下降后 1.8 秒内降至目标层，发送队列 P95 保持在 120 ms 内；恢复后 6 秒升层且无关键帧风暴”，而不是只写“弱网表现良好”。
